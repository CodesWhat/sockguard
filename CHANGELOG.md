# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **The marketing site and docs site record acquisition attribution.** `save_campaign_params` and `save_referrer` are enabled, and the `before_send` allowlist forwards the five `utm_*` values plus `$referring_domain` on `$pageview` and `$pageleave`. The referrer is transmitted at hostname granularity only: `$referrer` is never copied onto the outgoing envelope, because a full referrer URL can carry a path from a private page. A `$referring_domain` that is not a bare hostname is dropped rather than trimmed, and the `gclid`/`fbclid`/`msclkid` click identifiers that `save_campaign_params` collects are excluded. Neither option uses browser storage, so the cookieless posture is unchanged and no consent banner is required.

### Fixed

- **The sitemap and the pkg.go.dev badge no longer point at the wrong thing.** `/docs/podman` and `/docs/roadmap` are live and linked from the docs navigation but appeared in none of the sitemap's `<loc>` entries, because the docs slug list is hand-maintained while the comparison slugs are derived. The list now mirrors `docs/content/docs/meta.json` and a test fails when the two drift apart. The Go Reference badge built its pkg.go.dev URL from the GitHub-cased repository slug, which 404s there because pkg.go.dev keys on the case-sensitive `go.mod` module path; it still rendered a valid-looking badge, so the dead link was invisible until clicked.

### Documentation

- `sockguard_listener_up` is documented in the metric reference; it was published by the code but absent from the table.
- The Podman guide no longer describes its Kubernetes-YAML scope boundary in terms of v1.6.
- The roadmap records the Go module major-version path as a v2.1 track. `go.mod` has no `/v2` suffix, so the Go module proxy rejects every v2 tag and still resolves `@latest` to v1.7.5.

## [2.0.0] - 2026-08-28

v2.0.0 promotes `2.0.0-rc.4` after the exact candidate passed the four-hour
soak and all three published-image tri-tool conformance rows. Proxy behavior
is unchanged from rc.4, and the GA delta is release metadata plus
release-contract tooling and tests. The Helm image digest is temporarily clear
for the cut, so the chart falls back to `appVersion: "2.0.0"` until the stable
multi-arch manifest exists and can be re-pinned on the active development line.

### Security

- **Signed-policy trust now comes from a separate bootstrap file selected out of band.** A signed candidate can no longer select, replace, or disable the keyed or keyless trust that authenticates it; v1 deployments must split trust from candidate policy and add `--policy-bundle-trust-config` before upgrading.
- **Native Podman builds and mediated BuildKit sessions are fail-closed at their real trust boundaries.** `/libpod/build` constrains primary and additional contexts, host-facing writes, networking, Dockerfile instructions, and owner labels, while BuildKit state is isolated by verified caller principal, selected profile, and bounded session identity.

### Fixed

- **The composed proxy is hardened across request, response, listener, ownership, and observability paths.** Body and upgrade deadlines survive middleware wrappers, Unix sockets are removed only by inode ownership, collection keywords cannot bypass resource authorization, generated errors clear stale representation headers, and attacker-controlled methods and routes cannot grow metric cardinality.
- **The Helm chart supports the v2 signed-policy boundary directly.** Candidate policy, bootstrap trust, and signature objects mount separately; incomplete or conflicting references fail at render time; and signed listener settings remain inside the authenticated candidate.
- **Release publication and candidate qualification are fail-closed and reliable.** GitHub release pages publish and read back the tagged release notes, image provenance persists its linked artifact metadata, and RC4 verification proved 18 release assets with bundle-only signature artifacts plus matching signed images on GHCR, Docker Hub, and Quay. The exact candidate completed the four-hour soak with all three load workers at zero errors and reached the final RSS and thread assertions.
- **Release tags and complete Helm image metadata are revalidated at publication time.** The tag-triggered publisher requires stable tags to equal the protected default-branch head and prereleases to equal the matching development or maintenance head, so the documented manual path cannot bypass promotion. The Helm gate rejects duplicate and unsupported YAML shapes, preserves unspaced hashes in plain scalars, requires the shipped image repository, and proves the default chart renders the complete versioned image reference.
- **Soak qualification owns every process it starts.** The four-hour run retains Harden Runner telemetry without triggering its hosted-runner reclamation bug, waits only for finite load workers, and terminates and reaps those workers if qualification fails early.
- **Local fuzz staging copies only source inputs.** Tracked and nonignored working-tree files reach every worker while ignored worktrees, secrets, and build output stay out of the copied tree.

### Changed

- **v2 release blobs use sigstore bundles only.** Source and per-platform archives plus `checksums.txt` publish `.sigstore.json` bundles and documented `verify-blob --bundle` paths; the v1.7 transition-only detached `.sig` and `.pem` assets are retired.

## [2.0.0-rc.4] - 2026-08-28

### Fixed

- **Hostile registry signature metadata now stops at explicit input limits.** Image trust caps every registry GET response at 4 MiB, including redirect destinations; the referrers index at 32 descriptors; distinct signature images at 16; layers per signature manifest at 32; aggregate verification candidates at 16; aggregate annotation keys and values at 256 KiB; each simple-signing payload at 1 MiB; and all payload reads for one image at 16 MiB. Any count or byte-limit breach rejects discovery, even when a valid sibling exists. `enforce` denies the request, while `warn` logs the failed discovery and forwards it. Signature references must resolve directly to an image manifest; OCI indexes are rejected instead of recursively traversed, and payload layers with alternate URLs are rejected before blob resolution can fan out. Legal media-type parameters on direct image manifests are normalized before validation. Signature images are processed as they are discovered instead of retained as an attacker-sized slice.
- **Sigstore verification now honors cancellation without detaching crypto work.** Image-trust and signed-policy verification check the effective context before beginning and after each synchronous Sigstore verification attempt, reject a result that finishes after cancellation, and stop before later candidates or signer fallbacks. For image trust, `verify_timeout` also bounds registry fetching and preserves deadline or cancellation diagnostics instead of reporting the image as unsigned. Sigstore-go's local verification API cannot preempt an individual crypto call, and TUF root downloads keep their separate 15-second HTTP bound.
- **Signed-policy inputs are bounded and restricted to regular files before parsing or verification.** All YAML configuration files now stop at 16 MiB, while Sigstore bundle JSON stops at 4 MiB. Startup and reload open inputs nonblocking and reject FIFOs, devices, directories, and other non-regular paths, so an unverified candidate cannot block the process before its signature gate. Oversized inputs are rejected before Viper, protobuf JSON, or crypto can allocate from the full file.
- **Production policy-bundle keyless trust now loads the public Sigstore root through the existing process-wide TUF loader.** Keyless-only and mixed keyed/keyless bootstrap configs no longer stop at the previously unwired trust-material guard; the no-cache, bounded client loads initially and refreshes about every 24 hours, startup fails closed if the initial load fails, and a failed background refresh keeps the last valid root. Keyed-only policy-bundle trust loading remains offline. Successful audit attribution now records the verified certificate SAN rather than the configured subject regex.
- **The signed-policy signing examples now separate private signing state from the runtime.** Keyed examples supply an out-of-band `--key`, keyless CI examples use `--yes` and call out GitHub Actions OIDC permission, and the runtime never needs the private key or a writable TUF cache.

## [2.0.0-rc.3] - 2026-08-28

### Fixed

- **The four-hour soak no longer loses its GitHub-hosted runner to Harden Runner's block-mode control-plane bug.** The long-running workflow retains runtime telemetry in audit mode until [step-security/harden-runner#679](https://github.com/step-security/harden-runner/issues/679) is resolved; both earlier v2 candidate attempts ended with that upstream 10-to-24-minute reclamation signature before the final RSS-growth assertion could complete.

## [2.0.0-rc.1] - 2026-08-27

### Security

- **Signed policies now pin trust in a separate bootstrap file instead of trusting the policy to authenticate itself.** `sockguard serve --policy-bundle-trust-config <path>` is now required for signed-policy mode. The bootstrap file reuses the existing `policy_bundle` schema for `enabled`, keyed or keyless trust roots, Rekor inclusion, and the verification timeout; the signed candidate carries the reloadable `signature_path` in its own `policy_bundle` block. The candidate and trust config must be different files, including after symlink and hardlink resolution. Candidate copies of trust fields are ignored, the operational logger is not constructed until verification succeeds, and `policy_bundle.enabled` in the candidate without the new flag fails closed.
- **Signed policies can no longer be changed after verification by Tecnativa compatibility variables.** Startup rejects any rule-generating Tecnativa or LinuxServer variable in signed-policy mode, including section variables, `POST`, `GRPC`/`SESSION`, and granular `ALLOW_*` variables. Reload preserves the active policy and records `result="reject_compat"` if one appears after startup. Unsigned compatibility mode is unchanged.
- **Native Podman builds now use a complete fail-closed build inspector and owner stamping.** `POST /libpod/build`, including version-prefixed requests, is covered by `request_body.build`: every primary remote and `networkmode` value is checked, current repeated and legacy JSON `additionalbuildcontexts` are parsed, URL/image contexts require `allow_remote_context`, and Dockerfile `RUN` instructions remain denied unless allowed. Host volume controls, local-path additional contexts, multipart local contexts, and `rusage` output to a daemon-host `rusagelogfile` require `insecure_allow_body_blind_writes`; malformed, empty, unsupported, or duplicate values stay denied with every acknowledgment enabled. Ownership mode injects or replaces the configured owner label on Podman build output just as it does for Docker's classic builder.
- **Owner isolation and read visibility now treat collection keywords according to method and exact path.** Resources named `create`, `prune`, `json`, and similar Docker action words remain real resource identifiers on inspect and trailing-action paths. Cross-owner actions and hidden reads for those names no longer bypass their checks. Attestation statement gating now follows daemon boolean semantics too: empty, `0`, `no`, `false`, and `none` are false; every other non-empty value requests the protected statement and needs `response.allow_attestation_statements: true`.
- **Mediated BuildKit state is now scoped to a trusted caller principal, selected profile, and BuildKit session ID.** Verified client certificates correlate TCP connections across changing source ports, Unix peers remain distinct by kernel credentials, and unauthenticated TCP falls back to the normalized remote host. Solve ref ownership and upload IDs are admitted atomically, simultaneous builds from one caller cannot consume each other's state, and any registered mediated method without a dispatcher fails closed instead of falling through to raw forwarding. Session, ref, and upload identifiers are capped at 256 bytes before persistence; one control tunnel can admit at most 256 distinct BuildKit session IDs; and an abandoned one-use upload grant expires after one hour without shortening the valid post-control-close callback window.

### Fixed

- **Inspected request bodies and attach/exec upgrade handshakes now have effective 30-second deadlines.** Access logging and metrics preserve `http.ResponseController` deadline support, so a slow client cannot pin a body inspector by dribbling bytes through either wrapper. Attach and exec-start apply client-read plus upstream read/write deadlines until a valid `101 Switching Protocols` response, then clear them for the long-lived stream.
- **Unix listener shutdown no longer removes a replacement socket.** Automatic unlink-on-close is disabled for main, legacy, and admin Unix listeners; cleanup removes a path only when its current inode is the one Sockguard created. The same owned-inode cleanup runs on listener setup rollback and ownership-change failures.
- **Visibility filtering now returns clean generated errors and avoids duplicate inspections.** Replacement `502` JSON clears stale upstream representation headers such as `Content-Length` and `Content-Encoding`. A single-resource container or image policy combining label and name/image selectors decodes both from one bounded side-channel inspect instead of issuing two serial daemon calls.
- **The Helm chart can deploy the new signed-policy boundary without post-render customization.** Paired external Secret/ConfigMap references mount bootstrap trust and the candidate's sigstore bundle at separate fixed paths. Trust cannot reference the chart-generated candidate ConfigMap, signed listener settings live in the candidate YAML instead of discarded environment overlays, incomplete or conflicting references fail rendering, and rotation notes never expose trust contents.
- **BuildKit bridge churn no longer deadlocks under Go 1.27.** `golang.org/x/net` moves to v0.58.0, which carries the upstream HTTP/2 `ClientConn.Reserve` mutex fix from issue #80680. The bridge teardown regression now separately bounds tunnel completion and every concurrent caller under the race detector.
- **The JavaScript release gate now runs without configuration or image-performance warnings.** Biome's schema and recommended-rules setting match the locked 2.5.10 CLI, and the committed light/dark star-history SVGs render through Next.js image handling with explicit intrinsic dimensions while preserving the existing theme switch.
- **Release cuts now enforce the full source-branch contract.** Push and pull-request verification covers the protected `dev/*` and `maintenance/*` families, maintenance pull requests receive the required Grype, Govulncheck, and Gosec scans, stable tags are restricted to the protected default branch, and prereleases must use the matching development or maintenance line. Renovate validation follows a selected maintenance branch instead of forcing `dev/vX.Y`. The workflow can no longer wait for branch CI its trigger could never create or publish GA directly from an unpromoted development commit.
- **The tri-tool `current-edge` conformance row boots again on current portwing (#347).** Portwing hardened its edge client to refuse a plaintext (`http`/`ws`) controller URL unless `ALLOW_INSECURE_EDGE_URL=true`. The `examples/compose/tri-tool/docker-compose.edge-exec.yml` bundle points portwing at `http://drydock:3000` — a co-located service on the bundle's private compose network, reached over plain http by design — so on current portwing the service failed to load config and aborted pristine-boot/auth-handshake, skipping every edge assertion (weekly run 32702530383, `FAIL`). The opt-in is now set on the shipped edge-exec example and on the harness's unknown-key probe (`run-matrix.sh`), which starts a throwaway portwing with the same URL.
- **The scheduled ZAP baseline no longer fails on by-design WARN noise for the static site (#347).** sockguard's first `Security: ZAP Baseline` run (32710188160) failed on seven `WARN-NEW` alerts with `FAIL-NEW: 0`. All are informational or intended for a static public marketing+docs site: SPA/cache/CDN notices (10109, 10015, 10050), private IPs that are documentation samples (2), permissive CORS on public assets (10098), `script-src unsafe-inline` forced by the Next.js static export (10055), and a missing optional COEP header (90004). Each gets an `IGNORE` with a per-alert justification in `.zap/rules.tsv`, extending the existing 10049 suppression and mirroring drydock's `.zap/rules.tsv`; no header safely clears these on a static export, and none is a real exposure on a site with no auth or sensitive content.
- **The Helm chart's default image is re-pinned to the published 1.7.5 multi-arch manifest-list digest.** The pin was cleared for the v1.7.5 cut because the digest can't exist before the release images publish; with `codeswhat/sockguard:1.7.5` live on Docker Hub, `values.yaml` now pins `1.7.5@sha256:5b1f74e768516289841ba74630fd8527ac60c63159f34ecd9c1bb241e3ff101c`, resolved with `docker buildx imagetools inspect`, per RELEASING.md's Helm section.

### Performance

- **Request metric labels are now strictly finite.** Known HTTP methods retain their names, every other method collapses to `OTHER`, every unknown route family collapses to `unknown`, and unrecognized actions inside known container, image, swarm, plugin, and other families use finite `{action}` templates. Attacker-controlled methods or path segments can no longer grow the in-memory registry or scrape work without bound.
- **BuildKit frame reads use one framing allocation at the configured maximum size.** Streaming and unary decoders now read directly into the payload portion of the final frame buffer instead of retaining a second full-size copy.

### Tests

- **The affected security and composition paths now have behavioral regression coverage.** Tests prove an allow-to-deny hot reload changes live authorization, assigned profiles enforce resource limits and rate limits, `/grpc` and `/session` dispatch through their assigned BuildKit policy, OCI referrers-only and reconstructed keyless signatures verify end to end, and a primary transport error demotes the endpoint through `Resolver.RoundTrip`. BuildKit registry stress tests cover atomic Solve admission, bounded persistent state, expiry, and session correlation under the race detector. Release-contract tests execute the published-asset verifier against local stand-ins and require source, archive, and checksum bundle verification separately.

### Changed

- **v2 release blobs use sigstore bundles only.** The source tarball, per-platform archives, and `checksums.txt` each retain their cosign `.sigstore.json` bundle and documented `verify-blob --bundle` verification path. The v1.7 transition-only `.sig`/`.pem` assets and their second signing and verification pass are no longer produced.
- **Signed-policy bootstrap is an intentional v2 compatibility break.** A signed candidate can no longer select or disable its own trust. Existing v1 deployments must move trust fields into a separate bootstrap file, re-sign the changed candidate bytes, and add `--policy-bundle-trust-config`; Helm users must also configure paired trust and signature references. This security boundary is why the work ships on the v2 line instead of as a v1 patch.
- **Security-sensitive routing now has one production source of truth.** Attach/exec hijack detection delegates to the filter matcher, mediated BuildKit forwarding requires an explicit dispatcher, and obsolete session-local ownership plus policy-blind service-admission helpers were removed so future callers cannot bypass the registry and active profile policy.

## [1.7.5] - 2026-08-23

v1.7.5 promotes `1.7.5-rc.1` to stable. The delta since the candidate is release and CI infrastructure only: a guard against unresolved git conflict markers in tracked files (#336), the two fixes below, and the v1.7.5 metadata stamp, in which the Helm chart's default image digest pin is temporarily cleared — `image.tag` falls back to `appVersion` until the 1.7.5 images are live and the multi-arch manifest-list digest can be resolved and re-pinned per RELEASING.md's Helm section. Headlines, all carried from the candidate: the `TaskTemplate.Networks` host-network deny (#332), three closed build-time RUN-instruction gate bypasses (#333), closed cross-owner attestations access and two stale identity caches (#334), image-trust goroutine-leak and cross-repo signature-transplant hardening (#335), Grype scanning of the published multi-arch image (#318), rekor v1.5.4 removing `openpgp` from the build graph (#326), and dual-published sigstore bundle signatures ahead of cosign's legacy-format removal (#308).

### Fixed

- **Nightly and weekly Go quality jobs no longer die on harden-runner's egress block (#338).** `quality-fuzz-nightly.yml`, `quality-soak-weekly.yml`, `quality-go-bench-monthly.yml`, `quality-mutation-monthly.yml`, and `security-grype.yml`'s `govulncheck` job allowed `proxy.golang.org:443` but not `storage.googleapis.com:443`; `proxy.golang.org` serves module zips via signed redirects to that host, and the 1.26.6 toolchain bump invalidated the module cache, so the redirect got hit on a cold cache instead of being absorbed silently. Runs 32632014919 (Deep Fuzz nightly) and 32624289342 (Soak weekly) both failed in test setup with `domain not allowed: storage.googleapis.com.` fetching `github.com/klauspost/compress@v1.19.1`. `storage.googleapis.com:443` is now in every affected allowlist.
- **The conflict-marker scan skips tracked symbolic links instead of reading through them (#341).** `scripts/check-conflict-markers.mjs` read every `git ls-files` entry with `readFileSync`, which follows symlinks — a tracked link pointing at an unbounded target like `/dev/zero` would hang the scan, and a link out of the repo would scan foreign content. Each entry is now opened with `O_NOFOLLOW` and checked with `fstat` on the descriptor actually read, so a symlink is rejected at open and the check can't race a swap of the path — git itself stores a symlink as its target path, which can't contain a marker line, so nothing legitimate is skipped.
- **`release-cut.yml` now refuses to cut a prerelease tag when dispatched on the default branch (#337).** v1.7.5-rc.1 was cut with the workflow dispatched on `main` after merging `dev/v1.7` in, leaving `main` on a prerelease and the daily `Main Is Released` monitor failing — the rc tag is already published and can't be unwound. A new guard step, placed right after the tag string is computed (covering both the explicit `release_tag` input and the auto-computed path), fails with `::error::` when the resolved tag is hyphenated and `github.ref_name` matches the repository's default branch.

## [1.7.5-rc.1] - 2026-08-22

### Security

- **Swarm service host-network deny now covers `TaskTemplate.Networks` (#332).** The host-network guard only inspected the deprecated top-level `ServiceSpec.Networks`; the modern `TaskTemplate.Networks` field that `docker service create --network` actually populates was never modeled in the decode struct, so a service spec placing a `host` target there was silently dropped and bypassed `allow_host_network: false`, attaching the service to the host network. Both `/services/create` and `/services/{id}/update` now decode and deny a `host` target under either field.
- **Duplicate-`Dockerfile` build-context tars and frontend-less BuildKit Solves can no longer bypass `allow_run_instructions` (#333).** Three build-time RUN-instruction gate bypasses are closed. The `POST /build` inspector returned the first `Dockerfile` entry in the context tar while the daemon extracts and builds from the last, so a benign-first, `RUN`-bearing-second tar evaded the gate — it now denies on any duplicate `Dockerfile` entry (deny-on-ambiguity, with path names canonicalized so `/`- and `./`-prefixed variants collide). A raw-LLB Solve with an empty frontend buried `ExecOp`s in serialized op bytes outside the mediator's inspection scope — a bounded-depth LLB walk now denies any `ExecOp`, and any op that fails to decode, when `allow_run_instructions` is false. And an upload-session HTTP context routed around the hold-and-inspect Dockerfile stream — that exemption is removed, so those contexts now fall under the same remote-context restriction as any other.
- **Cross-owner image-attestations access and two stale identity caches are closed (#334).** `GET /images/{name}/attestations` mis-parsed the identifier and fell through both owner-label and visibility enforcement; the `/attestations` subresource is now recognized like `/json` and subject to the same checks. The visibility inspect cache no longer memoizes positive lookups, so a resource name deleted and recreated under a different owner within the 10s TTL can no longer serve the prior owner's verdict. The client-ACL per-IP cache now re-verifies that a cached container is still live before trusting it, so a torn-down container's ACL can no longer apply to a different container that reused its IP.
- **Image-trust verification is hardened against a goroutine leak and a cross-repo signature transplant (#335).** The keyless trust-root loader built the sigstore TUF-backed root once per call, leaking a background-refresh goroutine and ticker on every hot-reload across every keyless-configured surface and able to hang reload or shutdown; it is now memoized to at most one build per process, with failures left un-memoized so verification stays fail-closed and retryable. Separately, cosign verification bound only the manifest digest, so a signature valid for one repository also verified for the same digest copied into an attacker-controlled repository — verification now requires the payload's `docker-reference` identity to name the repository actually being pulled.
- **Grype now scans the published multi-arch image, not just from-source builds (#318).** Both existing Grype surfaces — `ci-verify.yml`'s required PR-time gate and `security-grype.yml`'s scheduled `grype-image` job — `docker build` from source and scan that, single-platform. Neither ever touched the actual multi-arch manifest users pull from GHCR/Docker Hub/Quay, so a CVE present only in a published-platform layer (a different resolved base-image digest, or an arm64-only issue a single-platform CI build never produces) was invisible to every gate. `release-from-tag.yml` gains a `release-image-scan` job that runs after the image publishes and is signed: it resolves the tag docker/metadata-action just pushed, reads the manifest list via `docker buildx imagetools inspect`, and runs Grype against each platform's resolved digest (`linux/amd64`, `linux/arm64`) straight from the registry, failing on the same HIGH/CRITICAL threshold the existing gates use. `security-grype.yml` gains a parallel scheduled pair (`resolve-latest-release` + `grype-published-release`) that resolves the latest published, non-prerelease tag via `gh release list` and scans it the same way, so a CVE disclosed against an unchanged published image surfaces between releases too. Both scan ghcr.io only — GITHUB_TOKEN reads it with no extra secret, and docker.io/quay.io carry the identical multi-arch manifest `release` pushes to all three registries. SARIF uploads to code scanning under per-platform categories, same as the existing `grype-image` job.

### Changed

- **rekor is bumped to v1.5.4, which removes `golang.org/x/crypto/openpgp` from sockguard's build graph entirely (#326).** rekor v1.5.4 migrates its `pkg/pki/pgp` to the maintained ProtonMail go-crypto fork (sigstore/rekor#2883); `go mod why golang.org/x/crypto/openpgp` now reports the main module does not need the package, and `govulncheck -test ./...` shows zero symbol-level results for GO-2026-5932 even under test-binary reachability. The package was only ever reachable from test binaries via sigstore-go's `testing/ca` fixture helper, never from the shipped proxy. This is hygiene, not a fix for Scorecard code-scanning alert 8: that advisory has no fixed version by design (golang/go#44226 keeps the deprecated package published forever) and Scorecard's OSV scan matches the x/crypto module's presence without call analysis, so the alert was dismissed separately as a structural false positive with the evidence recorded on it and on #326.
- **Release blob signing dual-publishes the new sigstore bundle format alongside the legacy `.sig`/`.pem` pair, ahead of cosign dropping the legacy `sign-blob` output flags (#308).** v1.7.3 (#271) opted the `signs:` blocks in `app/.goreleaser.yaml` and the source-tarball signing step in `release-from-tag.yml` out of cosign v3's new defaults with `--new-bundle-format=false --use-signing-config=false`, which was a stay of execution: cosign's own deprecation text says the bundle format "will be the only supported format in future versions." Two new `signs:` blocks (`cosign-keyless-bundle`, `cosign-keyless-archives-bundle`) run a second, independent `cosign sign-blob --bundle=...` invocation against `checksums.txt` and each per-platform archive using cosign v3's own defaults, producing a `.sigstore.json` file alongside the existing `.sig`/`.pem` pair; the source tarball's signing step in `release-from-tag.yml` does the same with two direct `cosign sign-blob` calls, replacing the previous single call that tried `--new-bundle-format=false --bundle` and then reverse-engineered `.sig`/`.pem` out of the resulting legacy-format bundle with `jq`/`openssl` when cosign didn't emit them directly — that fallback is gone now that a dedicated legacy-format invocation produces the pair directly. `scripts/verify-published-release.sh` (QA-6) downloads and verifies both forms for the source tarball, the per-platform archive, and `checksums.txt`; `docs/content/docs/verification.mdx` documents `--bundle` as the primary command with the legacy pair called out in a callout as a v1.7-line-only transition path; `RELEASING.md`'s "After tagging" section describes the dual-publish. Both forms are dual-published for this v1.7 line only — the legacy `signs:` blocks, the legacy sign-blob call, and the docs' legacy callouts are scheduled for removal in v1.8 once the bundle format has burned in on a real tag, per the standing house rule that a sigstore round trip is only provable on an actual tagged cut. Verified locally: `goreleaser check` validates the updated `.goreleaser.yaml`; `cosign sign-blob --yes --bundle <path> <artifact>` followed by `cosign verify-blob --bundle <path> <artifact>` round-trips cleanly against a local key pair on the exact cosign version this repo pins (`v3.1.3`), confirming the flag surface; `node --test scripts/verify-published-release.test.mjs` passes, including new assertions that the dry-run plan and asset list cover the `.sigstore.json` files; `actionlint` and `zizmor` are clean on the modified workflow. The keyless GitHub Actions OIDC signing flow itself — and thus whether the *published* bundle verifies against the documented identity regex end to end — only exercises on a real tag, same as the v1.7.2/v1.7.3 archive-signing work before it.

### Added

- **`release-cut.yml` and `release-from-tag.yml` now fail a release when the tag disagrees with the release-facing metadata files.** `scripts/release-metadata.test.mjs` only ever asserted the website version, Helm chart version/appVersion, README banner, and CHANGELOG heading agree with *each other* — it never read the tag being released, so all four files could agree while being stale relative to reality. That's exactly how v1.7.1 shipped claiming 1.7.0 (#304). ### Security

- **BuildKit gRPC mediation, phase 1: schema and policy foundation (#185).** v1.6.0-rc.1 added an opt-in acknowledgment (`insecure_accept_opaque_buildkit_tunnels`) for the uninspectable `POST /session`/`POST /grpc` BuildKit tunnel; this phase lays the groundwork for actually mediating it instead of just acknowledging it. `internal/buildkitproto/` vendors a pinned, curated subset of BuildKit v0.32.0's protobuf schema (Control's Solve/Status plus the LLB op graph, session auth/secrets/ssh/filesync/upload, and the gRPC health service) via a reproducible `buf`+`protoc-gen-go` generation script, committed with a provenance manifest and a golden test pinning the vendored files' checksums. `internal/buildkitproxy` adds a committed method-classification registry (mediate/passthrough/deny) covering every RPC either endpoint exposes, deny-by-default for anything unlisted (LLBBridge, nested Control/Session, containerd content, OTLP trace, Exporter, PolicyVerifier, and the rest of Control's admin surface all have no enabling knob). A new nested `request_body.buildkit` config block (`control.{allow_info,allow_list_workers,allow_status,solve.allow}` and `session.{health,auth,secrets,ssh,file_sync,file_send,upload}`) works at the top level and per client profile, exactly like every other `request_body.*` surface, and is mutually exclusive with `insecure_accept_opaque_buildkit_tunnels` — mediation supersedes the wholesale ack. There is no runtime mediator yet: configuring `request_body.buildkit` only changes which startup validation path admits a `/session`/`/grpc` rule, and the actual request-time behavior for both endpoints remains an unconditional deny, same as an unacknowledged config today. Full runtime mediation lands in later phases of the #185 epic.
- **BuildKit gRPC mediation, phase 2: h2c termination and stream routing (#185).** `internal/buildkitproxy` gains a real mediator: a hijacked `POST /session`/`POST /grpc` upgrade is now terminated as h2c on both sides (`golang.org/x/net/http2`'s `Server.ServeConn` against the Docker client, `Transport{AllowHTTP:true}` dialing the daemon) and bridged at the `http.Handler` level, one gRPC stream per `*http.Request`, preserving original bytes verbatim — no protobuf re-encoding yet. `POST /session` keeps the reversed roles the BuildKit wire protocol requires: buildkitd becomes the gRPC client, dialing back into the CLI's own session server over the same hijacked connection. Every stream is classified through phase 1's registry: a `Deny`-classified method is rejected in-stream with a gRPC `PERMISSION_DENIED` status and never reaches either peer; `Mediate`/`Passthrough` methods additionally have to clear a new `Policy.Allowed` gate — the per-field `request_body.buildkit` switches (`Control.Solve.Allow`, `Session.Secrets.Allow`, etc.) now actually enforce at request time instead of only gating startup validation, closing what would otherwise be a gap where any single configured field forwarded every other Mediate/Passthrough method for free. `filter/buildkit.go`'s unconditional deny on `/session`/`/grpc` is replaced with admission into the mediator once `request_body.buildkit` is configured; the literal `/moby.buildkit.v1.Control/<Method>` probe path (no upgrade, no tunnel) stays hard-denied regardless of the method's own classification, since there is no h2c connection there to mediate. The client's `X-Docker-Expose-Session-Grpc-Method` advertisement is rewritten to strip any service with no admitted method before it reaches the daemon. Defense-in-depth DoS caps bound concurrent streams and a denied-stream budget over a rolling window; exceeding either tears the whole tunnel down, while a single denied/oversized stream does not. A session registry keyed by client identity plus profile (never the client-supplied UUID alone, which is recorded only as advisory metadata) tracks open tunnels; per-ref state is a phase 3+ concern. Any bridge-level protocol or transport error closes the tunnel outright — Phase 2 never falls back to opaque proxying. `golang.org/x/net` moves from an indirect to a direct dependency (mediation path only; `google.golang.org/protobuf` was already direct, and no gRPC client library is introduced). `internal/buildkitproxy` is at 100% statement coverage.
- **BuildKit gRPC mediation, phase 3: `Control/Solve`/`Control/Status` per-message mediation and ref ownership (#185).** `Control/Solve` and `Control/Status` — phase 2's last two blanket byte-verbatim `Mediate` methods — now get real per-message policy decisions instead of a category-level pass. Each `Solve` call is read as a single buffered gRPC frame (a nonzero compression flag or any framing violation denies `buildkit_protocol_error`; an oversized declared length denies before the bytes are even read), decoded with the vendored `buildkitproto` stubs, and checked field by field: `security.insecure` is denied outright with no v1.7 enabling knob, `network.host` requires `allow_host_network`, and any entitlement string outside that fixed pair is denied as unrecognized; the frontend must be `""` (raw LLB) or `dockerfile.v0` (`gateway.v0` stays denied — it is `LLBBridge`'s only invocation path, itself hard-denied surface); every `FrontendAttrs` key must be on a fixed allowlist or the whole call denies `buildkit_schema_unsupported`, with a remote `context`/`context:<name>` value gated on `allow_remote_context` and `force-network-mode=host` gated on `allow_host_network`; cache imports/exports and exporters are checked against five new `request_body.buildkit.control.solve` allowlists (`allowed_cache_import_types`, `allowed_cache_export_types`, `allowed_cache_registries`, `allowed_exporters`, `allowed_exporter_registries` — empty means deny, same convention as every other `request_body.*` allowlist), with a `registry`-typed cache entry or a pushing `image` exporter additionally checked against the registry-host allowlists. On admission, the client's original frame bytes are forwarded untouched — never a re-encoded message. Protobuf unknown-field bytes anywhere in the decoded message tree (detected via reflection, recursing through nested messages, map values, and list elements) deny `buildkit_schema_unsupported` rather than passing an unreviewed future field through silently. Beyond the synthesis's own checklist, three surfaces are denied outright with no enabling knob at all, since each would otherwise let a structurally "known" field bypass the allowlists above or reach other hard-denied surface: the pre-v0.4.0 deprecated singular cache-ref fields, `EnableSessionExporter` (the session-exporter negotiation path into the hard-denied `moby.exporter.v1.Exporter`), and any non-empty `SourcePolicy` (image-reference rewrite rules that could otherwise route around sockguard's own registry allowlists). The session registry gains a ref-ownership index keyed by `SessionKey` (client identity + profile — never a client-supplied ref alone): `Status` decodes its ref and denies `buildkit_ref_not_owned` unless that ref was registered by an admitted `Solve` from the same identity+profile, refs are released when their owning session closes, and a per-session cap (`Limits.MaxRefsPerSession`, default 256) bounds how many distinct refs one session can register. `allow_run_instructions` has no phase 3 equivalent: a `dockerfile.v0` Solve never puts RUN instructions in the `SolveRequest` itself, and a frontend-less Solve buries them in opaque serialized LLB op bytes outside this phase's scope. `internal/buildkitproxy` stays at 100% statement coverage.
- **BuildKit gRPC mediation, phase 4: credential session mediation for Auth/Secrets/SSH (#185).** The `POST /session` RPCs buildkitd calls BACK into the client for to obtain credential material now get per-message decode and policy mediation, closing the last blanket byte-verbatim `Mediate` methods that could hand out registry tokens, secret payloads, or SSH agent access unexamined. `moby.filesync.v1.Auth`'s four RPCs are gated on the already-existing `request_body.buildkit.session.auth` allowlists, now actually consumed for the first time: every RPC's `Host` must match `allowed_registries` (normalized the same lowercase/`index.docker.io`→`docker.io` way as Solve's cache/exporter registry lists, so config-side case doesn't silently fail to match); `FetchToken` additionally requires its `Realm` to match `allowed_realms` and every requested scope to be a member of `allowed_scopes` — researched against BuildKit's own authorizer, a registry's token realm commonly lives on a different host than the registry itself (Docker Hub challenges to `auth.docker.io` for a `registry-1.docker.io` pull), so the registry-host allowlist alone cannot bound where a resulting bearer token is minted for. `moby.buildkit.secrets.v1.Secrets/GetSecret` is gated on an exact `allowed_ids` match; a non-empty `annotations` map is denied outright — BuildKit v0.32.0's stock secret request/response path never populates or reads that field, so there's no reviewed semantics to admit. `moby.sshforward.v1.SSH/CheckAgent` is gated the same way on `allowed_ids`; `ForwardAgent` (a bidirectional stream of raw agent-protocol bytes with no unary message to decode) is gated on the agent ID carried in gRPC metadata (`buildkit.ssh.id`, BuildKit's own wire convention) BEFORE a single byte is relayed, and the stream itself is never decoded, buffered as a message, or logged in either direction — only the ID that admits it is inspected. On admission every RPC forwards the client's original frame bytes verbatim, exactly like phase 3's Solve/Status; every response — which for these RPCs carries the actual credential/secret/token content — is never decoded on any path. A new per-session quota (`Limits.MaxCredentialCallsPerSession`, default 512) throttles Auth/Secrets/SSH call volume independent of the connection-wide denied-stream abuse budget, since an admitted call never trips that budget; exceeding it denies `RESOURCE_EXHAUSTED`/`buildkit_credential_call_limit_exceeded` without counting against the abuse budget. Audit events for these RPCs carry the registry host in the clear (low-cardinality, operator-facing) but only a truncated SHA-256 of secret/SSH-agent IDs, never the raw identifier. `internal/buildkitproxy` stays at 100% statement coverage.
- **BuildKit gRPC mediation, phase 5: FileSync/FileSend/Upload file and upload stream mediation (#185).** `moby.filesync.v1.FileSync/DiffCopy`, `moby.filesync.v1.FileSend/DiffCopy`, and `moby.upload.v1.Upload/Pull` — the three remaining byte-verbatim streaming `Mediate` methods — now get per-message decode/policy mediation instead of an unexamined relay, built on a new streaming primitive (`streamRelayReader`/`relayValidatedFrames`) that decodes each gRPC length-prefixed frame in turn, validates it, and forwards the original bytes verbatim on admission — never a re-encoded message, matching phase 3's own convention extended to a multi-message stream. `FileSync/DiffCopy` is verified directly against `tonistiigi/fsutil` and `moby/buildkit`'s own source (not just the vendored descriptors): buildkitd's request direction carries only `PACKET_REQ`/`PACKET_FIN`/`PACKET_ERR` (structural validation only), while the response direction carries every `PACKET_STAT` (path) and `PACKET_DATA` (file bytes) — every Stat path/symlink target is checked for absolute paths, `..` traversal, and embedded NULs (`buildkit_path_rejected`), and new caps bound file count, per-file bytes, total bytes, and path length (`request_body.buildkit.session.file_sync.{max_files,max_total_bytes,max_path_length,max_file_bytes}`, threaded through `Limits`/`Policy` via a new `effectiveLimits` per-session merge). The one stream named `dir-name: dockerfile` (buildx's own literal value for the Dockerfile-only sync, distinct from `context`) gets hold-and-inspect: each file's `PACKET_DATA` is buffered independently by its fsutil-assigned ID — never per-stream, since fsutil's real sender interleaves multiple files' data across four parallel workers — until that file's own EOF chunk, then the SAME RUN-instruction/syntax-frontend inspection the classic `/build` path applies runs against the reassembled bytes; a denial discards every held byte for that file without releasing anything downstream, an admission flushes the exact original frames. Holding is skipped entirely when `allow_run_instructions` is already set, mirroring the classic path's own early exit. `FileSend/DiffCopy` (the daemon exporting a build's output back to the client) is admitted only when the calling session has an admitted `Control/Solve` on record (`buildkit_session_mismatch` otherwise) and gets a pure byte-count cap with **no** decode of any kind — `moby/buildkit`'s own server dispatches FileSend to one of two different wire shapes depending on the negotiated exporter (`fsutil.Packet` for a local/`-o type=local` export, `BytesMessage` for a tar/OCI export) with no signal sockguard can see to tell them apart, so decoding either shape risks misinterpreting or spuriously denying the other. `Upload/Pull` (a client-streamed stdin/remote-context upload) is bound to a one-use token: an admitted `Solve`'s `FrontendAttrs` naming a `context`/`context:<name>` value shaped like `http://buildkit-session/<id>` registers `<id>` as a one-use key for that `SessionKey`, and a `Pull` must present the matching `urlhost`/`urlpath` metadata and consume it atomically — a second `Pull` for the same id, or one that was never admitted, denies `buildkit_upload_token_invalid`; Upload's `BytesMessage` frames, unlike FileSend's, are genuinely unambiguous and get the same decode-plus-unknown-fields check as every other mediated message, plus a byte cap (`request_body.buildkit.session.{file_send,upload}.max_bytes`). `FileSync/TarStream` stays hard-denied with no new knob. Completing the RUN-inspection story this hold-and-inspect path is built for, `Control/Solve` now also denies a genuinely-remote (git/HTTP) build context when `allow_run_instructions` is off — buildkitd fetches the Dockerfile from that URL itself, so no FileSync stream ever carries it to inspect, exactly the case classic `POST /build` already refuses; a local `http://buildkit-session/<id>` upload is excluded, since its Dockerfile still arrives over the inspectable `dockerfile` stream. Unknown protobuf fields anywhere in a mediated message still deny `buildkit_schema_unsupported`; file contents are never logged, and a denial's gRPC message is always fixed text, never a client-supplied string. `internal/buildkitproxy` stays at 100% statement coverage.
- **BuildKit gRPC mediation, phase 6a: fuzzing, goroutine-leak, and DoS-budget hardening (#185).** Adversarial and concurrency coverage for the phase 1–5 mediator, with no production code changes. Five native fuzz targets exercise unary gRPC framing, `Control/Solve`/`Control/Status` mediation decisions, h2c upgrade validation, and `X-Docker-Expose-Session-Grpc-Method` advertisement rewriting. Goroutine-leak checks cover every bridge teardown path (admitted, denied, and error-close), `SessionRegistry` gets concurrency stress beyond the existing 500-iteration race test, and new boundary tests pin `MaxConcurrentStreams`, size-cap, and idle-timeout DoS budgets plus slow-reader/fast-writer backpressure in both tunnel directions. `internal/buildkitproxy` stays at 100% statement coverage.

## [1.6.0-rc.1] - 2026-08-05

First release candidate for v1.6.0. The v1.6 line delivers the full roadmap sequence: multiple independently scoped main listeners (#149), fail-closed declarative admission mutations (#151), effective-state resource-limit guarantees for container updates and Swarm services (#152), Engine API 1.55 validation plus the Compose/BuildKit transport acknowledgment (#153), first-class Podman support across both the Docker-compatible and native `/libpod` API surfaces — body inspection, ownership isolation, read-side visibility, a `podman-readonly.yaml` preset, and a dedicated Podman guide (#148) — and the published Sockguard + Portwing + drydock tri-tool conformance matrix that now gates GA promotion (#150).

### Security

- **BuildKit's opaque session/gRPC tunnel now requires an explicit acknowledgment.** `docker compose build` / `up --build` route through Buildx's hijacked, unversioned `POST /session` and `POST /grpc` streams by default (Engine API 1.53 deprecated both; current Buildx still uses them) — a transport sockguard cannot bound or inspect once opened, unlike `POST /build`'s single JSON body. Startup validation now denies any rule that would admit `/session`, `/grpc`, or a `moby.buildkit.v1.Control` method path (mirroring `validateBodyBlindWriteRules`/`validateReadExfiltrationRules`) unless the new `insecure_accept_opaque_buildkit_tunnels: true` is set — a dedicated flag, not folded into `insecure_allow_body_blind_writes`, because the risk is an uninspectable stream rather than an unbounded body. Tecnativa's `GRPC=1`/`SESSION=1` compat env vars keep working unchanged: `ApplyCompat` auto-sets the new flag with a deprecation warning when either is present. New `drydock-with-build.yaml` / `portwing-with-build.yaml` presets ship the classic-builder (`DOCKER_BUILDKIT=0`, fully-inspected `POST /build`) alternative on top of the respective `-with-compose.yaml` baseline. Full BuildKit gRPC mediation is deferred to a v1.7 epic.
- **`POST /containers/create` mount validation closes three Engine API 1.45–1.55 gaps.** A `HostConfig.Mounts` entry whose `Type` is not `bind`/`volume`/`tmpfs`/`image` is now denied fail-closed instead of passing through unexamined. `VolumeOptions.Subpath` (1.45+) and `ImageOptions.Subpath` (1.55+) are validated as clean, non-escaping relative paths. `TmpfsOptions.Options` (1.46+) entries that re-enable `exec`/`dev`/`suid` on a tmpfs mount are denied unless the new `request_body.container_create.allow_tmpfs_privileged_options` is set.
- **Network policy covers two more Engine API fields.** `POST /networks/create` with an explicit `EnableIPv4: false` (1.48+) is denied unless the new `request_body.network.allow_disable_ipv4` is set. Endpoint `GwPriority` (1.45+, which network provides the default route) is now covered by the existing `allow_endpoint_config` gate on both `POST /networks/*/connect` and `POST /containers/create`'s `NetworkingConfig.EndpointsConfig`.
- **`GET /images/{name}/attestations?statement=true` is denied by default.** Attestation statements can carry SBOM/provenance content generated by a different, potentially less-trusted pipeline than the image itself. The response filter now rejects the full statement payload unconditionally unless the new `response.allow_attestation_statements` is set; listing available attestation manifests (no `statement=true`) is unaffected.
- **New `response.redact_host_topology` option (opt-in).** Redacts `GET /info` host-fingerprinting fields — kernel version, OS, architecture, host name, and daemon labels — independent of Swarm mode.
- **`X-Registry-Auth` and `X-Registry-Config` headers are now bounded-decoded before use.** `POST /images/create`, `POST /images/*/push`, and `POST /build` decode these base64 headers (standard, URL-safe, and unpadded variants) under an 8 KiB cap; oversized, non-base64, or non-JSON values are denied fail-closed instead of forwarded unexamined. When `image_pull.allowed_registries` is configured, the decoded `X-Registry-Auth` `serveraddress` must canonicalize to an allowlisted host. Decoded credential fields are never inspected, logged, or reflected in a deny reason.

### Fixed

- **`stripVersionPrefix` now strips Podman's three-part semver API version prefix (e.g. `/v5.0.0/`), not just Docker's `vN`/`vN.N`.** The path normalizer that runs before every rule match consumed at most one optional `.N` group, so a request through a versioned Podman `libpod` client (which sends its full daemon semver, major.minor.patch) fell through with the version prefix still attached and could never match a `/libpod/**`-shaped rule. No shipped preset or default config allows any `/libpod/` path today, so this had no live impact yet — it's a groundwork fix ahead of #148's libpod routing support (path predicates and default-deny coverage land in this same change; body inspectors and a configurable `/libpod/` policy surface are separate, later PRs). `internal/metrics`'s independent `stripVersionPrefix` (used only for the low-cardinality `route` metric label) already handled three-part versions correctly and needed no change.

### Added

- **Fail-closed declarative admission mutations (`mutations.rules[]`).** A bounded, config-driven rule set can now inject fixed labels or remap a matched image reference on `POST /containers/create`, `POST /services/create`, and `POST /services/update` before every existing body inspector, image-trust verification, and owner-label stamping runs — so a mutated image reference still flows through registry-allowlist and image-trust policy exactly as if the client had sent it directly. Each rule supports exactly one operation (`inject_labels` or `remap_image`, never both) and an independent `enforce`/`warn`/`audit` rollout mode; `warn`/`audit` rules are evaluated against a cloned document and never touch the forwarded request body. The strict subtree decode rejects unknown keys and weak YAML type coercion, and validation rejects overlapping rules, oversized rule sets, and any attempt to inject the reserved owner-label key. New reason codes: `mutation_request_invalid`, `mutation_request_too_large`, `mutation_apply_failed`, `mutation_postcondition_failed`.
- **`listeners:` — multiple independently scoped main listeners from a single process (#149).** Configure a list of named listeners (unix socket and/or mTLS TCP, in any combination) instead of the single top-level `listen:` block, each with its own `allowed_profiles` admission scope. A request whose resolved client profile isn't in the listener it arrived on's `allowed_profiles` is denied (`403`, `listener_profile_not_allowed`) even if the base policy would otherwise permit it — the same credentials never get a weaker fallback path on the wrong listener. `listen:` and `listeners:` are mutually exclusive; `listeners:` is YAML-only (no `SOCKGUARD_LISTENERS` env override, matching the existing `rules:`/`clients.profiles` precedent). All main listeners share one handler chain and hot-reload generation; `allowed_profiles` is the only per-listener field a reload may change — renaming, adding, removing, or rebinding a listener requires a restart. `admin.mount_on` is newly required when the in-band admin endpoints (`admin.enabled` with no dedicated `admin.listen`) ride a config with 2+ effective listeners, so enabling admin never silently widens its exposure to every listener. Observability gained a `listener` label on the request/duration/deny metric families, a new `sockguard_listener_up{listener,role,network}` gauge, a `listeners` array on `/health` (state per listener: `bound`/`serving`/`draining`/`failed`/`stopped`, 503 if any required listener isn't serving outside an intentional drain), and `listener_name` fields on the access and audit logs. New `configs/multi-listener.yaml` preset demonstrates a CI-scoped and an ops-scoped unix socket listener with disjoint profiles.
- **Resource-limit guard for container update and Swarm service writes (`request_body.container_update.require_memory_limit`/`require_cpu_limit`/`require_cpu_limit_hard`/`require_pids_limit`, `request_body.service.require_cpu_limit`/`require_cpu_limit_hard`, all opt-in, default off).** A new post-ownership policy layer validates the *effective* resource state a write would produce, not just the fields the request happens to touch. For `POST /containers/*/update`, it fetches the container's current state from the daemon and merges the submitted update the same way Docker does — omitted or zero scalar `HostConfig` fields (`Memory`, `NanoCpus`, `CpuQuota`, `CpuPeriod`, `CpuShares`) leave the current value unchanged, while `PidsLimit` is a pointer, so any submitted value including `0`/`-1` is an explicit clear — and is enforced only when `request_body.container_update.allow_resource_updates: true` is also set; sockguard now warns (not errors) at startup/reload if a require_* flag is set without that gate. For Swarm services, an ordinary create/update validates the submitted `ServiceSpec` directly (Swarm has no partial merge), while `POST /services/*/update?rollback=previous` validates the daemon's stored `PreviousSpec` instead — the daemon reactivates that document verbatim and ignores the submitted body — returning `409 resource_limit_policy_state_changed` on a version mismatch, and a submitted `UpdateConfig.FailureAction: "rollback"` additionally validates the current `Spec` against an automatic rollback. Malformed requests (`400 resource_limit_request_invalid`), failed daemon lookups (`502 resource_limit_policy_lookup_failed`), and rollback version conflicts (`409 resource_limit_policy_state_changed`) are hard errors in every rollout mode; only a genuine policy violation (`403 resource_limit_policy_denied`) honors a profile's `warn`/`audit` rollout mode. Denial messages are static and parameter-free. Access and audit logs gain optional `resource_policy_*` fields, populated only for requests the guard actually evaluated. See the [configuration docs](https://getsockguard.com/docs/configuration) for the full merge semantics and the "ratchet" migration note — enabling a require_* flag against an already-noncompliant legacy container or service blocks its next guarded write until a compliant patch supplies the missing limit.
- `app/testdata/docker-api/max-supported-version.txt` pins the Engine API version sockguard has been validated against (currently `1.55`), read by both a new regression test and the monthly `quality-api-version-watch.yml` CI workflow, which fetches Docker's public Engine API version-history page and fails the job loudly when a newer version is documented than the pin covers.
- **`POST /libpod/containers/create` body inspection (`request_body.libpod_container_create`, #148).** Podman's native SpecGenerator create endpoint gets its own body inspector, structurally separate from `container_create` and routed exclusively off `isLibpodContainerCreatePath` — the libpod and Docker-compat bodies use incompatible top-level shapes (`privileged`/`netns`/`mounts`/`volumes`/`devices`/`cap_add`/`user`/`sysctl` vs. nested `HostConfig`/`Config`), and neither inspector reads a byte of the other's shape, closing the fail-open risk a shared or path-inclusive matcher would create. Gates mirror `container_create`'s where a libpod field maps onto the same semantics: privileged, host netns/pidns/ipcns/userns, a `restrict_namespace_sharing` allowlist for `{"nsmode":"container","value":"<ref>"}` joins, bind-mount and device path allowlists (named `volumes[]` entries are never bind-gated), a `cap_add` allowlist, non-root user, read-only rootfs, memory/CPU/PIDs limits from `resource_limits`, seccomp/AppArmor allowlists, `deny_selinux_disable`, and `image_trust` (the same cosign verify → digest-pin flow as `container_create`, applied to the `image` field). Two libpod-only gates have no Docker-compat analog: `allow_systemd_mode` denies any `systemd` value but the explicit `"false"` by default — SpecGenerator's own default is `"true"` even when `--systemd` is never passed by the client — and `allow_custom_id_mappings` denies a non-default `idmappings.uidMap`/`gidMap` or `--userns=auto`. Field names and default values (including the `systemd`/mounts-vs-volumes-casing/sysctl-singular/device-path-unsplit quirks) are pinned from real captured `POST /libpod/containers/create` request bodies in `app/internal/filter/testdata/libpod/*.json` (Podman 6.0.2 client / Podman Engine 5.8.1 server), not from documentation, resolving a field-name ambiguity (`ipcns` vs. `ipc`) that had been unresolved prior to this capture. All gates default fail-closed. Builds on #148's route predicates from the prior PR1.
- **libpod (Podman-native) body inspection for pod create, exec, and volume/network/secret create (#148).** `POST /libpod/pods/create` gains a dedicated inspector (`request_body.libpod_pod_create`) covering the pod-level host network namespace (`allow_host_network`, default deny), a shared PID namespace (`allow_shared_pid_namespace`, default deny), and the infra image's registry (`allowed_infra_image_registries`, reusing the same allowlist shape as `image_pull`); cross-owner pod-membership checks are now covered by the ownership PR below rather than deferred. `POST /libpod/containers/{name}/exec` and `POST /libpod/exec/{id}/start` now route through the exact same `execPolicy` that already guards the Docker-compat exec paths — libpod and Docker exec bodies share Docker's field names on the wire, so `request_body.exec` is the single config surface for both route families; a new libpod-path exec-inspect upstream call (`GET /libpod/exec/{id}/json`) backs the libpod exec-start decision the same way the existing Docker-path call does. `POST /libpod/volumes/create`, `POST /libpod/networks/create`, and `POST /libpod/secrets/create` get libpod-shaped decode structs reusing the existing `request_body.volume`/`network`/`secret` config under new `request_body.libpod_volume`/`libpod_network`/`libpod_secret` keys — libpod's wire shapes differ from Docker's compat API (e.g. volume options live under `Options` not `DriverOpts`, network options are snake_case with no swarm-mode fields, and secret creation reads `driver` from the query string rather than a JSON body) but the same allow/deny knobs apply. Startup validation's blind-write gate now also covers all of the above plus `POST /libpod/play/kube` (and its `/libpod/kube/play` alias), `POST /libpod/kube/apply`, and `POST`/`PUT /libpod/manifests/*` — none of which get a request-body inspector in this release, since full Kubernetes-YAML/PodSpec modeling is out of scope for v1.6, so admitting any of them requires the existing `insecure_allow_body_blind_writes` acknowledgment; a single allowed `POST /libpod/play/kube` can provision an arbitrary number of privileged containers from one manifest sockguard never parses, which is a materially larger blast radius than the single-container blind writes that flag otherwise covers. The read-exfiltration gate (`insecure_allow_read_exfiltration`) is extended with libpod's container archive/export/logs/attach and image export/get/push surface, plus `GET /libpod/generate/kube` (a read despite the name — Podman registers it as a GET that dumps existing pod/container definitions to YAML, which can leak environment variables and other resource data) and manifest-list registry pushes (`POST /libpod/manifests/*/registry/*` and the deprecated backward-compat `POST /libpod/manifests/*/push`) — both push local manifest content to a caller-selected registry, an exfiltration surface despite being writes at the Docker API layer.
- **Owner-label isolation and read-side visibility now cover the libpod surface (#148).** `POST /libpod/containers/create`, `POST /libpod/pods/create`, `POST /libpod/networks/create`, and `POST /libpod/volumes/create` get the configured owner label injected into their (lowercase-keyed) `labels` field the same way Docker-compat create endpoints do; `POST /libpod/volumes/create` is the one exception — Podman's `VolumeCreateOptions` has no JSON tags on its labels field, so it serializes as capitalized `Labels` and is stamped accordingly. `POST /libpod/secrets/create` has no JSON body at all (`driver`/`label` are query parameters), so it reuses the existing query-param stamping path unchanged. A new `KindLibpodPod` resource kind gives pods — which have no Docker-compat equivalent — their own list/inspect owner-filtering and visibility-policy coverage; libpod network inspect responses are unwrapped from Podman's occasional single-element-array envelope before label extraction. Every libpod list and inspect/action path (containers, pods, networks, volumes, secrets) is now owner-filtered and visibility-filtered, closing off `/libpod/`-native paths as a bypass around Docker-compat's existing isolation. Cross-owner pod-membership checks land here: `POST /libpod/pods/create` requests that join another owner's namespaces are denied, and `POST /libpod/containers/create` requests that target another owner's pod (`SpecGenerator.pod`) are denied — the same `container:<ref>` namespace-sharing and embedded-resource-reference checks Docker-compat create already applies, extended to libpod's uniform `{"nsmode":"container","value":"<ref>"}` namespace object and `pod`/`infra_image` fields. Denial reasons for libpod-family requests carry a `libpod ` prefix, matching the convention the libpod body inspectors already use.

## [1.5.0-rc.2] - 2026-07-20

### Security

- **Owner isolation now authorizes workload dependencies embedded in create/update bodies.** `POST /containers/create` resolves the requested image, named bind/structured volumes, custom `NetworkMode`, every `NetworkingConfig.EndpointsConfig` network, and existing `container:<ref>` namespace targets. `POST /services/create` and `/services/*/update` resolve the task image, named volumes, attached networks, secrets, and configs. A reference carrying another owner's label or a dependency Docker cannot resolve is denied before Docker sees the request; only a successfully resolved but unlabeled image can use `ownership.allow_unowned_images`, while other unlabeled resource types remain untrusted. Create new owned volumes/networks/secrets/configs through their owner-stamping endpoints before attaching them.
- **Ownership authorization no longer caches positive inspect results for mutable Docker names or tags.** Every authorization-critical lookup now observes current daemon state, closing the deterministic window where a deleted/recreated resource name or retagged image could inherit the previous object's cached owner. The bounded singleflight cache remains on visibility-only reads.
- **Registry pushes now require the existing explicit exfiltration acknowledgement.** Startup validation treats `POST /images/*/push` and `POST /plugins/*/push` like archive/export and log/attach surfaces: although they are Docker API writes, they read local artifacts and transmit them to a caller-selected registry. `insecure_allow_read_exfiltration` retains its legacy name for compatibility and now documents this broader scope.
- **The production website and `/docs` export now receive a hosting-layer browser security policy.** Root `vercel.json` applies an enforced CSP, `nosniff`, clickjacking denial, strict referrer handling, a restrictive permissions policy, HSTS, and legacy XSS-filter disablement to every route. The CSP permits only same-origin scripts/connections, exact external badge/image hosts, and the inline bootstrap/styles required by the static Next.js output; `unsafe-eval` and external script origins remain disallowed.
- **Helm defaults now independently enforce the image's non-root identity and seccomp confinement.** The DaemonSet pod security context defaults to `runAsNonRoot: true`, UID/GID `65532`, and `seccompProfile.type: RuntimeDefault`; adding the host Docker socket GID through `supplementalGroups` merges with and preserves those controls.
- **`POST /containers/create` now enforces the same endpoint-config policy `POST /networks/*/connect` already did — closes a policy bypass.** `network.allow_endpoint_config` (default `false`) has always gated a network-connect's static IP, MAC address, and driver options, but `POST /containers/create`'s own `NetworkingConfig.EndpointsConfig` was never inspected at all — the identical config on a container's create-time network sailed through unchecked. A client (or a compromised/misbehaving updater) could bypass the connect-side gate entirely by putting a static IP, custom MAC, or driver opts on the *create* call instead of a follow-up connect. `containerCreatePolicy` now applies the same check to every entry of `NetworkingConfig.EndpointsConfig` (iterated in sorted key order for deterministic denial messages), reusing the connect-side check via a new shared `denyEndpointConfigReason` helper. Both endpoints continue to share the single `request_body.network.allow_endpoint_config` flag — no new YAML key.

### Changed

- **Endpoint `Aliases` are no longer gated by `allow_endpoint_config` — a deliberate relaxation.** `POST /networks/*/connect` used to deny non-empty `EndpointConfig.Aliases` unless `allow_endpoint_config: true`, but Docker Compose sets `Aliases: [serviceName]` on *every* endpoint it creates, so this broke every multi-network Compose recreate under the default policy — and Aliases were never enforced on `POST /containers/create`'s primary network either (the only inspector that previously existed), making the connect-side gate a bypassable, low-value control rather than a real guarantee. Aliases are now always allowed, on both `POST /networks/*/connect` and the new `POST /containers/create` check above. `Links` (joining another container's linked alias namespace — a materially different, higher-privilege primitive) remains gated exactly as before.
- **Migration note:** deployments that were relying on the *pre-existing gap* — an unchecked static IP, custom MAC, or endpoint driver options reaching the daemon via `POST /containers/create`'s primary network (bypassing the connect-side `allow_endpoint_config` gate) — must now set `request_body.network.allow_endpoint_config: true` explicitly, the same flag that already controlled this at connect time. This is also the fix for the real-world failure that motivated this change: an updater (e.g. drydock) recreating a macvlan-attached container with a static IP had its `POST /networks/*/connect` call for the container's network correctly denied by the existing connect-side gate, orphaning the update on the old network — `drydock.yaml` and `drydock-with-compose.yaml` now document the required `allow_endpoint_config: true` opt-in for exactly this case. Plain multi-network recreates that only carry `Aliases` (the Compose-driven common case) need no config change and now work by default.

## [1.5.0-rc.1] - 2026-07-10

### Added

- **`examples/compose/tri-tool/` — the full sockguard → Portwing → drydock stack in one compose file.** Sockguard filters the Docker socket (unix-socket mode, same embedded preset as `examples/compose/portwing/`); Portwing reads sockguard's proxied socket instead of mounting `/var/run/docker.sock`; drydock never touches Docker at all — it connects to Portwing over HTTP in Standard Mode (`DD_AGENT_PORTWING_HOST`/`PORT`/`SECRET__FILE`, `DD_LOCAL_WATCHER=false`) and gets every container fact secondhand, already filtered. The Portwing<->drydock shared secret is a single Docker secret mounted into both containers (`TOKEN_FILE` / `DD_AGENT_PORTWING_SECRET__FILE`) rather than a plaintext env var. Defaults to no exec (the plain `portwing` preset); the README notes the `portwing-with-exec.yaml` preset and drydock's experimental Edge Mode as the variants this bundle deliberately doesn't ship.
- **Compose-oriented presets: `portwing-with-compose.yaml` and `drydock-with-compose.yaml`.** Deploying a Compose stack *through* portwing (or drydock's agent) against a sockguard-filtered socket needs Docker API operations the base presets deny — `docker compose up`/`down` creates and removes project networks and named volumes as part of any stack that declares them. The new presets layer exactly those rules on top of `portwing.yaml`/`drydock.yaml`: `POST /networks/create`, `DELETE /networks/*`, `POST /networks/*/connect` + `/disconnect`, `POST /volumes/create`, `DELETE /volumes/*`. They deliberately continue to deny `/build` — Compose's BuildKit fallback needs `/session` + `/grpc` pass-through this preset does not model, so `--build` workflows need a further variant (documented in the preset headers). Like the exec variant, compose-deploy support is a separate opt-in rather than a change to the base presets.
- **Helm chart: pod-level `podSecurityContext` support.** The DaemonSet previously exposed only a container-level securityContext, so there was no chart-native way to grant the non-root (UID 65532) sockguard container the host Docker socket's group. The chart now renders a pod-level securityContext with a documented `supplementalGroups` placeholder (`stat -c '%g' /var/run/docker.sock` to find the GID) — the same pattern portwing's Kubernetes manifests use.
- **`request_body.container_create.require_cpu_limit_hard`** — a new, independent, opt-in bool (default `false`) that requires a genuine CPU-time cap (`HostConfig.NanoCpus` or `CpuQuota`) rather than just any CPU-budget knob. The existing `require_cpu_limit` treats `CpuShares` as equivalent to a real cap, but `CpuShares` only sets a container's relative scheduling *priority* under contention — on an idle or lightly-loaded host, a `CpuShares`-only container can still consume 100% of every CPU it can reach. Enabling `require_cpu_limit_hard` closes that gap without changing `require_cpu_limit`'s existing behavior at all; the two knobs are fully independent, so enabling the new one alone (without also setting `require_cpu_limit`) is a complete, supported configuration. A lone `CpuPeriod` (without `CpuQuota`) does not satisfy the new check either — it's only the denominator for `CpuQuota` and enforces nothing by itself. `cis-docker-benchmark.yaml` deliberately does not enable it: CIS 5.11 ("CPU priority set") is satisfied by `CpuShares` per the benchmark text itself, so forcing a hard cap there would reject CIS-5.11-compliant workloads.
- **Exec-create `Env` allowlisting/denylisting: `request_body.exec.allowed_env_vars` and `denied_env_vars`.** Two new opt-in list fields let operators restrict which environment variable *names* may appear on `POST /containers/*/exec` — `denied_env_vars` is checked first and always wins (even against an overlapping `allowed_env_vars` entry), and a non-empty `allowed_env_vars` denies any `Env` entry whose name isn't listed. Matching is exact, case-sensitive, and name-only — the value after `=` is never inspected, matched, or echoed into logs or deny responses, so secrets carried in an allowed variable's value never leak. Both fields default to empty, meaning **no restriction** (deliberately the opposite default from `allowed_commands`, which denies all exec once inspection is active), so this is a zero-behavior-change opt-in. Enforcement is create-time only: `GET /exec/{id}/json` never exposes the original `Env` and exec instances are immutable once created, so there's nothing for the existing `POST /exec/*/start` re-check to re-validate. See the exec section of the [security docs](https://getsockguard.com/docs/security) for a copy-pasteable example denylist (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `LD_AUDIT`, `DYLD_INSERT_LIBRARIES`, `PYTHONPATH`, `PATH`) targeting dynamic-linker/interpreter hijack vectors.
- **New opt-in structural gates for container-namespace-sharing modes in `request_body.container_create`.** `allow_host_network`/`allow_host_pid`/`allow_host_ipc`/`allow_host_userns` only ever matched the literal `"host"` value on `HostConfig.NetworkMode`/`PidMode`/`IpcMode`/`UsernsMode` — a `container:<id-or-name>` value (join **another container's** namespace) always passed through unchecked, and still does by default. `restrict_namespace_sharing` (+ `allowed_namespace_sharing_containers` allowlist) lets operators deny or scope down `container:<id>` joins structurally, independent of ownership; both default off/empty, so `container:<id>` values keep passing through unchecked unless explicitly enabled. `deny_namespace_path_mode` denies `NetworkMode` values with an `ns:<path>` prefix, a raw host-namespace-file attachment form that also bypasses the `"host"`-literal check entirely.
- **`request_body.container_create.allow_host_cgroupns`** — the one host-namespace mode the `allow_host_*` family didn't cover. `HostConfig.CgroupnsMode=host` shares the host's cgroup namespace, exposing the host cgroup hierarchy to the container (an information-disclosure and cgroup-escape vector), yet passed through uninspected — even as this release added the host-mode denial for `UTSMode` and the `container:<ref>` sharing gate. The new opt-in bool (default `false`) denies `CgroupnsMode=host`, consistent with `allow_host_network`/`pid`/`ipc`/`userns`; set it `true` to keep `cgroupns: host` working.

### Security

- **Closed a class of case-varied-JSON-key filter bypasses across every path that re-marshals a request body.** The daemon decodes create/update body keys case-insensitively and, on duplicate case-variant keys, honors the last one after re-encoding — and Go's `json.Marshal` emits map keys sorted, so a client's lowercase `"image"`/`"hostconfig"` sorts *after*, and overrides, the canonical key. Sockguard inspects a body via a case-insensitive struct decode, but several paths then mutate and re-marshal it through a map whose re-sort could move a shadow key into the winning position — so the daemon acted on a value the filter never saw. Pre-existing instances, all now closed:
  - **Owner-label spoofing** (`internal/ownership`, present since owner isolation shipped in v1.0): a lowercase `"labels"` object alongside the proxy-injected `"Labels"` let a client's forged `com.sockguard.owner` win at the daemon, claiming another owner's identity.
  - **Cross-owner namespace resolution** (the `container:<ref>` check new in this release): reading `HostConfig.NetworkMode`/`PidMode`/`IpcMode`/`UTSMode`/`UsernsMode` by exact case let a lowercase `"hostconfig"`/`"networkmode"` hide a namespace join from the cross-owner deny.
  - **Image-trust digest pinning** (`internal/filter`, present since v1.1.0): `POST /containers/create` and swarm `POST /services/create`+`/update` verified the struct-resolved image with cosign but wrote the pinned digest to the exact-case `"Image"` only, so a shadow `"image"` survived untouched, sorted last, and made the daemon pull an unverified image — a silent, total bypass of enforce-mode signature verification.
  - **Whole-body reorder** (`ownership` when `owner` is set; `filter` when `image_trust` pins a digest): re-marshaling the entire body re-sorted *any* duplicate case-variant field, so a shadow `"hostconfig"` (or a nested duplicate `"privileged"`) could flip a decision the filter already cleared — defeating every container-create/service rule (privileged, host namespaces, capabilities, devices, and the rest).
  The fix rejects fail-closed (`400`/`403`) any create/update body carrying duplicate case-variant JSON keys, checked recursively before the body is re-marshaled, and collapses a single lowercase variant to the canonical key so a legitimately-lowercased field is still inspected and pinned. Docker's case-*sensitive* data-map fields — `Labels`, `Annotations`, `Sysctls`, `Volumes`, `ExposedPorts`, `PortBindings`, network/IPAM `Options`, `DriverOpts`/`Opts`, `LogConfig.Config`, `EndpointsConfig`, IPAM auxiliary addresses — are exempt from the duplicate-key check at their own keys, since the daemon keeps those keys case-sensitively, so two case-varying keys there are distinct valid entries rather than a struct-field fold; the walk still descends *through* them, so a struct nested inside such a map (an `EndpointSettings`, an `IPAMConfig` array element) keeps its fold check. `strings.EqualFold` is a superset of the daemon's own JSON field folding for the ASCII field names involved, so no daemon-honored variant is missed.
- **`container:<id>` namespace-sharing targets are no longer invisible to owner-label isolation — this changes default behavior for `ownership.owner` deployments.** `HostConfig.NetworkMode`/`PidMode`/`IpcMode`/`UTSMode` (and, defensively, `UsernsMode`) can join **another container's** namespace via `container:<id-or-name>`, a form `allow_host_network`/`allow_host_pid`/`allow_host_ipc`/`allow_host_userns` never inspected (those gates only ever matched the literal `"host"` value, and still only do). When `ownership.owner` is configured, `POST /containers/create` now resolves every `container:<ref>` target and denies the request if that container belongs to a different owner — joining a foreign container's network/PID/IPC/UTS namespace is a full cross-tenant compromise (shared sockets, process visibility, shared `/dev/shm`), strictly worse than the access ownership already gates on every other endpoint. Same-owner references still pass; an unlabeled target is treated as untrusted and denied too (consistent with every other container-targeting ownership check), so only a same-owner join is allowed by default. **Unlike every other knob in this release, this is a deliberate default-behavior change, not an opt-in:** it only affects deployments that already set `ownership.owner` *and* already relied on cross-owner `container:` sharing — a pattern that is itself the vulnerability being closed. Restore the previous unchecked behavior with `ownership.allow_cross_owner_namespace_sharing: true`.

### Changed

- **`upstream.request_timeout` now defaults to `60s` instead of unlimited — affects anyone who never set this field explicitly.** The opt-in per-request deadline added in v1.2.0 — which bounds a hung upstream body or heavy read, returning `504` with `reason_code=upstream_request_timeout` — shipped disabled by default, so a wedged daemon could still pin a request indefinitely even though this feature exists specifically to catch that failure mode. Long-lived endpoints stay exempt (event streams, follow/stream logs and stats, image pull/build/push/load, plugin pull/push/upgrade, container export, image get, websocket attach, and the blocking `/containers/{id}/wait`), so builds, pulls, and log streams are unaffected by the new default. `GET`/`PUT /containers/{id}/archive` (`docker cp`) has been added to that exemption list as part of this same change, so a large `docker cp` into or out of a container is also unaffected by the new 60s ceiling. **To opt back out to the old unlimited behavior, set `upstream.request_timeout: "off"`** — a new literal that explicitly disables the deadline (the legacy empty string `""` still works too, for backward compatibility with configs written before `"off"` existed). Prefer `"off"` when disabling via `SOCKGUARD_UPSTREAM_REQUEST_TIMEOUT`: an explicitly empty env var is silently treated as unset by the config loader and falls back to the 60s default, whereas `off` always works. Configs that already set an explicit `upstream.request_timeout` (including an explicit `""`) are unaffected by the default change either way. The effective value is now also logged on startup (`upstream_request_timeout` field on the "sockguard started" log line) for visibility.
- **Config Viper-default registration is now generated by reflection off `Defaults()` instead of ~200 hand-maintained `v.SetDefault(...)` lines in `load.go`.** Every mapstructure-tagged config field is registered automatically from its struct tag and default value, so a newly added knob can no longer silently lose its `SOCKGUARD_*` environment-variable override by omission — the exact bug class already hit three times (`allow_sysctls`, four service-hardening rails, and the SELinux/`deny_unconfined_system_paths` trio). Auditing the reflection walker against the old hand-written list also surfaced two previously-undiscovered instances of the same gap, now closed as a side effect: `request_body.{container_create,service}.image_trust.{mode,allowed_signing_keys,allowed_keyless}` and `request_body.container_create.{allowed_device_cgroup_rules,allowed_device_requests}` had no `v.SetDefault` registration either. No YAML key, env var, CLI flag, or default value changes — behavior is bit-for-bit identical for every previously-working path, verified by a new reflection-driven completeness test plus the full existing `load_test.go` / `load_env_defaults_test.go` / `preset_test.go` suites.

### Fixed

- **The upstream-timeout long-lived classifier now parses `?follow=`/`?stream=` the way the daemon does.** The helpers matched only `1`/`true` (follow) and `0`/`false` (stream), but dockerd's `httputils.BoolValue` treats every value except `""`/`0`/`no`/`false`/`none` as true. So `GET /containers/{id}/logs?follow=yes` streams forever at the daemon yet was bounded by the new 60s `upstream.request_timeout` default and cut off with a spurious `504`, while `GET /containers/{id}/stats?stream=no` was misclassified as long-lived and wrongly exempted from the deadline. Both now use daemon-accurate `BoolValue`/`BoolValueOrDefault` semantics (stream still defaults to true when the parameter is absent), and plugin `pull`/`push`/`upgrade` join the long-lived exemption set alongside image pull/push. Pre-existing, but higher-impact now that the deadline defaults on.
- **`insecure_allow_body_blind_writes` is now wired into `filter.ExecOptions` — the flag actually does something at request time, not just at startup validation.** Previously, setting the flag satisfied the startup validator (`internal/cmd/rules.go`) but the exec body-inspection policy (`internal/filter/exec.go`) had no idea the flag existed: an empty `request_body.exec.allowed_commands` always denied every exec with `"exec denied: no commands are allowlisted"`, regardless of the flag. Default-deny is unchanged: the flag must still be set explicitly, and pinning `allowed_commands` (as `drydock-with-selfupdate.yaml` already does) needs no flag at all. Enabling the flag now also logs a startup warning (once per process, surviving hot-reload) naming exactly what it loosens.

## [1.4.0-rc.3] - 2026-06-22

Internal multi-axis audit of the v1.4 release candidate (security, performance, tests, supply chain) — no critical or high findings; this section collects the resulting hardening.

### Added

- **Swarm service SELinux confinement parity.** Two opt-in `request_body.service` knobs (default off, zero behavior change): `deny_selinux_disable` denies `ContainerSpec.Privileges.SELinuxContext.Disable=true` (the swarm equivalent of the container-create `label=disable` that turns off SELinux confinement), and `deny_selinux_label_override` denies any `SELinuxContext.{User,Role,Type,Level}` context customization. Closes the gap where an operator who enabled `deny_selinux_disable` for container creates got no equivalent enforcement against swarm services.

### Fixed

- **Plugin inspection now fails closed across the board.** `POST /plugins/{id}/set` denies a body that is valid JSON but not a `[]string` (previously such a body skipped the env-prefix/bind-mount/device allowlists entirely), and `POST /plugins/create` denies an archive with no inspectable `config.json` instead of forwarding it unchecked — both matching the deny-on-uninspectable posture every other inspector already uses.
- **Plugin-create gzip-bomb guard.** The `/plugins/create` archive walk now bounds the *decompressed* byte count (4 GiB cap) like the build and image-load paths, so a small compressed body can no longer expand to hundreds of GiB during the tar walk/drain and exhaust memory.
- **Right-sized plugin JSON body limits.** `/plugins/pull`, `/plugins/{id}/upgrade`, and `/plugins/{id}/set` now cap their (small JSON) bodies at 1 MiB instead of the 512 MiB archive limit, removing a per-request half-gigabyte heap-allocation DoS vector; the 512 MiB limit stays only on `/plugins/create`, which spools to disk. Oversized `/plugins/create` bodies now return `413` (was `403`), matching the build/node-update convention.
- **Service seccomp `Profile: null` no longer false-denies.** JSON `"Profile": null` decodes to the 4-byte literal `null` rather than an empty blob; the implicit-custom-profile fail-closed check now treats it as "no inline profile" so `deny_custom_seccomp_profiles` doesn't reject a bare `null`.
- **Clearer error when pinning a verified service image** that is missing `TaskTemplate`/`ContainerSpec`, instead of an opaque `unexpected end of JSON input`.
- **Node-update inspection now fails closed.** `POST /nodes/{id}/update` denied on a body it could not decode is now denied (was forwarded to Docker) — both the whole-body decode failure and a field-level type mismatch (e.g. `Role`/`Name` sent as a number, `Labels` sent as an array) return `node update denied: request body could not be inspected`, matching the deny-on-uninspectable posture every swarm inspector already uses.
- **`deny_unconfined_seccomp`/`deny_unconfined_apparmor` now win over a seccomp/AppArmor allowlist.** When both an allowlist and the deny-unconfined flag were configured, the allowlist branch short-circuited the deny check — so an allowlist that (mis)included `unconfined` silently let an unconfined profile through even though the operator had explicitly denied it. The deny-unconfined check now evaluates independently and takes precedence.
- **Response redaction now empties `HostConfig.MaskedPaths`/`ReadonlyPaths` under `redact_mount_paths`.** Those arrays expose the container's exact masked/read-only filesystem-hardening shape; they're now emptied alongside the existing `Binds`/`Mounts` source redaction so a read-side consumer under a mount-path redaction profile can't read them back.
- **Public-key pin comparison is now constant-time.** Client-certificate `public_key_sha256_pins` matching used a plain string compare; it now uses `crypto/subtle.ConstantTimeCompare` and evaluates every configured pin without early-return, so neither the digest bytes nor which pin matched is observable through timing.
- **Image-trust verification now derives its configured deadline when the caller set none.** Registry discovery observes the surrounding image-trust context directly. Sigstore-go verification is local and synchronous; v2.0.0 adds cooperative cancellation checks around those crypto calls.
- **Malformed cosign signature manifests now leave a debug breadcrumb.** `FetchCandidates` silently skipped a signature manifest it couldn't parse (correct — a sibling valid signature must still verify), but logged nothing; it now emits a debug log with the image ref, resolved digest, and parse error so a verification miss is distinguishable from a silently-dropped manifest.
- **`admin.listen.insecure_allow_wide_open` set purely via env var is no longer ignored.** The key had no `SetDefault` registration, and Viper only unmarshals registered keys, so `SOCKGUARD_ADMIN_LISTEN_INSECURE_ALLOW_WIDE_OPEN=true` with no config-file entry had no effect. It is now registered.
- **`reload.enabled`/`reload.debounce`/`reload.poll_interval` are now reload-immutable.** The watcher reads them once at startup to wire its fsnotify watch and debounce/poll timers, so changing them via a hot reload silently had no effect; a reload that mutates any of them is now rejected with a restart-required message instead.

### Changed

- **Startup warning for a patterns-only visibility policy.** A visibility policy with `name_patterns`/`image_patterns` but no `visible_resource_labels` selector now logs a warning at construction: pattern response-filtering only covers `/containers/json` and `/images/json`, so `/events` and the other list endpoints would stay unrestricted unless a label selector is added.
- **Clearer validation errors for the two global insecure acknowledgement flags.** The per-profile `insecure_allow_body_blind_writes` / `insecure_allow_read_exfiltration` validation messages no longer imply the flag lives on the profile — both now say it is a top-level (global) setting.
- **Startup warning for an insecure upstream Docker endpoint.** A `tcp://` upstream configured with `insecure_allow_plain_tcp` (unencrypted) or `insecure_skip_tls_verify` (unverified) now logs a warning at startup — for both explicit `upstream.endpoints` and the `DOCKER_HOST` env drop-in — so an accidental transport downgrade is visible rather than silent.
- **Startup warning for a rule pattern carrying a Docker API version prefix.** A rule whose `match.path` begins with `/vN.N/` (e.g. `/v1.45/containers/json`) can never match — sockguard strips version prefixes from the request path before matching — so it now warns once at startup with the offending pattern instead of being a silently-dead rule.

### Performance

- **Audit sampler no longer allocates on the hot path.** The `AuditSampler` stored last-emit timestamps as `*time.Time`, heap-allocating one on every `ShouldEmit` call (including the common in-window rejection branch). It now keeps a single `*atomic.Int64` (Unix nanos) per `(client, reason)` key, allocated once and mutated in place — the steady-state rejection branch is allocation-free.
- **Health probes now run concurrently.** The upstream failover resolver probed endpoints sequentially, so a stalled daemon delayed the health update for every other endpoint by up to one timeout. `probeAll` now fans out across endpoints, bounding a tick's cost to the slowest single probe.
- **Metrics middleware returns its pooled response writer on panic.** The pooled response writer and the request observation moved into a `defer`, so a panic in a downstream handler no longer leaks the writer back-pressure or drops the metric.
- **Smaller hot-path allocations.** Hijacked exec/attach requests forward the query string verbatim (`RawQuery`) instead of re-parsing and re-encoding it, and the Prometheus exposition sort keys compare field-by-field with `cmp.Or` instead of building throwaway `\x00`-joined strings per comparison. The duration-histogram observe path also increments `count` before its buckets so a concurrent scrape can never momentarily report a bucket larger than the count (Prometheus invariant).

### Tests

- **Multi-host hijack path now has integration coverage.** `HijackHandlerWithDialer` — the dialer-based hijack used by the multi-host upstream resolver — gets an end-to-end full-upgrade test (101 switch + bidirectional byte proxy through a mock dockerd over a unix socket), closing a 0%-covered branch, and the test drains the proxy's copy goroutines before returning so it never leaks a goroutine that races a sibling test's hook restore.

### Documentation

- **`HEAD /_ping`** is added to the recommended rules template — the Docker SDK/CLI pings with `HEAD` (falling back to `GET`), so a `GET`-only `/_ping` rule could leave the SDK's health check denied.
- **DOCKER_* drop-in TLS matrix is complete.** The multi-host guide now documents the fourth case — `DOCKER_TLS_VERIFY` set with no `DOCKER_CERT_PATH` → verified, server-auth-only TLS against the host's system root CAs with no client certificate — alongside the existing mTLS, skip-verify, and plaintext cases.

## [1.3.0-rc.3] - 2026-06-11

### Added

- **Swarm service create/update now enforces the container-create identity/privilege rails.** Four opt-in `request_body.service` knobs mirror their container-create counterparts onto the swarm `ContainerSpec`, closing a bypass where a service could request a workload posture that `/containers/create` would have denied: `require_non_root_user` (`ContainerSpec.User`), `require_no_new_privileges` (`ContainerSpec.Privileges.NoNewPrivileges`), `require_readonly_rootfs` (`ContainerSpec.ReadOnly`), and `require_drop_all_capabilities` (`ContainerSpec.CapabilityDrop` must include `ALL`). All default off. The root-user check reuses the same numeric-UID parsing as container-create, so zero-padded `"00"`/`"0:0"` forms are rejected. (Swarm has no privileged mode, per-service namespace sharing, or runtime/device selection, so those container-create rails have no service equivalent.)

### Security

- **Zero-padded numeric UIDs can no longer bypass root-user enforcement.** `require_non_root_user` (container create) and `allow_root_user: false` (exec) compared the user field to the exact string `"0"`, but Docker parses `Config.User` numerically — so `"00"`, `"000"`, or `"0000:5"` all run as root while slipping past the check. Both inspectors now parse the UID and treat any value resolving to 0 as root.
- **A wide-open dedicated admin listener is now a validation error, not just a startup warning.** A non-loopback plaintext admin listener with no `clients.allowed_cidrs` exposes candidate-YAML submission and policy metadata with no authentication and no IP backstop. Validation now rejects that shape unless the operator sets `clients.allowed_cidrs`, configures `admin.listen.tls`, or explicitly acknowledges the exposure with the new `admin.listen.insecure_allow_wide_open: true`.

### Fixed

- **A hot reload that rotates `policy_bundle.signature_path` no longer wedges every subsequent reload.** Bundle verification resolved the signature file from the last-applied config instead of the candidate, so changing `signature_path` (which is intentionally reload-mutable) loaded the wrong bundle, failed the digest check, and — because the active config only advances on success — left the operator permanently stuck until a restart. Verification now reads the path from the candidate config.
- **`SOCKGUARD_REQUEST_BODY_CONTAINER_CREATE_ALLOW_SYSCTLS` and the `image_trust.verify_timeout` env vars are no longer silently ignored.** Three `request_body` keys were missing their `SetDefault` registration, and Viper only unmarshals registered keys — so configuring those fields purely through their `SOCKGUARD_*` env vars (no config file) had no effect. All three are now registered.
- **Oversized `POST /nodes/{id}/update` and `POST /build` request bodies now return `413` instead of `403`,** matching every other body-limited inspector (a policy `403` implied the request was forbidden by rule rather than too large).
- **Release images now carry real `commit` and `built` metadata.** The release workflow's Docker build only passed the `VERSION` build arg, so `sockguard version` in published images reported `commit unknown / built unknown`. The workflow now passes `COMMIT` (the tagged SHA) and `BUILD_DATE` (UTC build timestamp) through to the existing ldflags wiring.
- **The container-label ACL exclusivity warning now fires once per process instead of on every hot-reload.** It was wired into the handler-chain build, which reruns on each config reload, so long-running deployments with reload enabled accumulated duplicate warnings. The warning is now gated by a process-lifetime guard (and finally has test coverage for both the enable-check and the once semantics).
- **Coalesced inspect-cache waiters now honor their own context.** A request that joined an in-flight upstream inspect blocked unconditionally until that inspect finished — a slow daemon could pin waiter goroutines past their own deadlines. Waiters now return `ctx.Err()` promptly on cancellation while the in-flight resolve (and its cache fill) continues for future callers.
- **`dockerfilters.Decode` now rejects `filters` parameters over 64 KiB before JSON parsing.** Real clients encode a handful of short terms; the only previous bound was the 1 MiB header limit.

### Changed

- **Test coverage for review-flagged gaps:** legacy (map-format) Docker filter encoding through the ownership and visibility rewrites end-to-end, the visibility meta-cache's one-inspect-per-TTL-window behavior, admin path-normalization variants on the policy-version interceptor (the validate interceptor already had them), and double-encoded `%252f` admin paths pinning the fail-closed pass-through. Corrected the visibility meta-cache code comment and the 1.3.0-rc.2 changelog wording: the cache accelerates repeated single-resource reads — list responses are filtered from their own payload and never inspect upstream.
- **Upstream inspect responses are now drained before close** on the ownership and visibility owner-isolation paths, so idle keep-alive connections to the daemon are reused instead of discarded after each inspect.
- **Corrected misleading exec comments in the `cis-docker-benchmark` and `gitlab-runner` presets** that referenced a non-existent `allowed_users` field; exec identity is controlled by `allow_root_user` and the argv `allowed_commands` allowlist.

## [1.3.0-rc.2] - 2026-06-10

### Security

- **Admin endpoint paths are now normalized before matching.** The validate and policy-version interceptors compared `r.URL.Path` to the configured path with an exact string match, so variants like `/admin/validate/` (trailing slash) or `/admin//validate` fell through to the Docker-API rule evaluator instead of being handled by the admin layer. Default-deny meant they were still rejected, but any future `/admin/**` allow rule would have exposed them upstream. Paths are now `path.Clean`-normalized on both sides, with regression coverage for trailing-slash, doubled-separator, and dot-segment variants.
- **Non-upgrade hijack responses strip hop-by-hop headers.** When the daemon rejects an attach/exec upgrade (non-101), the fallback response copied every upstream header verbatim — including `Connection`, `Upgrade`, `Keep-Alive`, and any header named in `Connection`, letting a hostile or misconfigured upstream inject connection-scoped headers into the client response. The fallback now applies the same hop-by-hop stripping the upgrade path already used.
- **Container-label ACLs now log an exclusivity warning at startup.** Label grants (`com.sockguard.allow.*`) are only trustworthy when sockguard is the *only* consumer of the Docker socket — a workload with raw socket access can create a container with arbitrary permission labels and self-grant access. Sockguard cannot detect other socket consumers, so enabling `clients.container_labels` now emits an explicit warning stating the invariant.

### Fixed

- **`Defaults()` and the load-time Viper defaults disagreed on `image_trust.require_rekor_inclusion`.** The Viper default was a hardcoded `true` while `config.Defaults()` returned `false` for the same field. Loading was unaffected (the Viper value won), but any consumer of `Defaults()` saw the wrong posture. `Defaults()` now carries `true` for both `container_create` and `service` image trust, and load defaults read from it — one source of truth.

### Changed

- **The Docker builder stage now cross-compiles (`--platform=$BUILDPLATFORM` + `GOOS`/`GOARCH` from BuildKit target args)** instead of running the Go toolchain under emulation for non-native platforms. Multi-arch builds get native-speed compiles; this also fixes Go runtime faults observed when emulating the amd64 toolchain under qemu/Rosetta.
- **`filters` query decoding is now a single shared decoder (`internal/dockerfilters`).** Ownership and visibility had drifted copies; the canonical version sorts legacy map-format (`{"label":{"k=v":true}}`) keys, so owner-label filter rewrites now produce deterministic ordering for legacy-format requests too.

### Performance

- **Name/image pattern visibility checks on single-resource reads no longer cost one daemon round-trip per request.** Resource-meta inspects (`name_patterns` / `image_patterns` axes on `GET /containers/{id}/json` and other single-resource paths) now go through the same TTL-LRU, request-coalescing cache as label lookups, so repeated polls of the same resource trigger at most one upstream inspect per 10-second TTL window. (List responses were never affected — they are filtered from their own payload without upstream inspects.)
- **File logging uses a 64 KiB buffer (up from 4 KiB),** cutting flush frequency and writer-mutex hold time on busy hosts; the 1-second periodic flush still bounds record staleness on quiet ones.

## [1.2.0] - 2026-06-02

### Added

- **Added an opt-in upstream readiness probe (`health.readiness.*`).** Both `/health` and the active watchdog judge the upstream by a raw socket *dial* — a liveness signal that only proves the socket accepts connections. That misses the failure mode behind a recent silent outage: the daemon kept accepting connections (so `/_ping` and the dial stayed green) while `GET /containers/json` hung, and every consumer that trusted health to stay accurate kept routing into a wedged proxy. The new readiness endpoint (`health.readiness.{enabled,path,interval,timeout}`, default `/ready`, **disabled** by default) issues a real `GET /containers/json?limit=1` through the shared Docker transport and reports **unready (HTTP 503)** on any transport error or non-2xx — returning `200` only when the daemon is actually answering the API. It reuses the existing Monitor state / watchdog / handler machinery; only the probe differs (a pluggable probe hook, leaving the dial path unchanged). Two new metrics mirror the watchdog and are emitted when `metrics.enabled` is also true: the `sockguard_upstream_api_up` gauge and the `sockguard_upstream_readiness_checks_total{result="ready|unreachable"}` counter. The whole `health.*` block remains reload-immutable, so readiness changes take effect on restart. Validation rejects a readiness path that collides with `health.path`, `metrics.path`, or `admin.path`, and requires positive `interval` / `timeout` durations.
- **Added `upstream.request_timeout` to bound hung proxied requests.** `ResponseHeaderTimeout` only caps the wait for upstream response *headers*; a Docker daemon that sends headers promptly and then hangs the body (or hangs a heavy read like `GET /containers/json`) can still pin a proxied request indefinitely — the same wedged-daemon failure mode the readiness probe detects. The new opt-in `upstream.request_timeout` (Go duration string, empty = disabled, validated as a positive duration) applies a total per-request deadline to ordinary finite requests; on expiry the transport aborts the upstream connection and the proxy returns **`504 Gateway Timeout`** (`reason_code=upstream_request_timeout`), distinct from the `502` an unreachable socket yields. Long-lived endpoints are exempt so the deadline never severs a legitimately long response: event streams, follow/stream logs and stats, image pull/build/push/load, container export, image get, websocket attach, and the blocking `/containers/{id}/wait`. Hijacked attach/exec-start connections already bypass this handler, and client cancellation (`context.Canceled`) keeps its existing `502` path. Unlike the `health.*` block, this field is reload-mutable (only `upstream.socket` is immutable), so it takes effect on hot reload.

## [1.0.0-rc.2] - 2026-05-16

### Changed

`request_body.exec.allowed_commands` entries are now argv templates whose tokens are matched as sockguard globs instead of by exact string equality. Each token follows the same dialect as path rules — `*` matches a run of non-slash characters, `**` matches any sequence — and a command is allowed when its token count equals an entry's and every token matches the glob at that position. This lets an operator allowlist an exec whose argv carries a variable component (a run ID, timestamp, or generated path) without enumerating every literal form, e.g. `["drydock", "finalize", "*"]`. Tokens with no glob metacharacters keep matching exactly as before; the only behavioral change is for an entry that literally contained `*` or `**` and relied on it being matched as a literal asterisk.

A non-loopback plaintext TCP listener now requires **two** insecure acknowledgments instead of one: `listen.insecure_allow_plain_tcp` (unencrypted transport) and the new `listen.insecure_allow_unauthenticated_clients` (any host that can reach the port can impersonate a client). One flag without the other is rejected at config validation, so the dangerous mode cannot be reached by a single fat-fingered flag. The same applies to `admin.listen.*`. Existing configs running plaintext non-loopback TCP must add `insecure_allow_unauthenticated_clients: true` (env: `SOCKGUARD_LISTEN_INSECURE_ALLOW_UNAUTHENTICATED_CLIENTS`). The previous standalone startup warning is removed — the two-flag validation gate replaces it.

A rule whose `match.path` contains a literal `%` is now a config-validation error instead of a startup warning. sockguard percent-decodes request paths before rule matching, so such a pattern can never fire against real traffic — a silently dead rule is a security-intent gap, so the misconfiguration now fails at load.

### Fixed

Oversized request bodies on the exec, plugin, and swarm inspectors now return `413 Request Entity Too Large` instead of `403`. These three were the remaining inspectors emitting a plain `403` for a body-size rejection while container-create, service, volume, network, and the others already returned `413`; all body inspectors now share one size-rejection contract.

### Security

Hardening from the 2026-05-16 branch review:

- The visibility pattern-filter response buffer (`GET /containers/json`, `/images/json` with `response.name_patterns` / `response.image_patterns`) is now capped at `filter.MaxResponseBodyBytes` (8 MiB). A larger upstream response is rejected with a `502` instead of being buffered unbounded, closing an out-of-memory DoS that every other body path already guarded against.
- The visibility middleware now honors rollout mode. An invisible single-resource inspect under `mode: warn` / `mode: audit` is forwarded to the upstream with a `would_deny` verdict instead of being hard-`404`'d, so operators can measure visibility-policy impact before enforcing — consistent with every other deny gate.
- The reverse-proxy and side-channel (ownership / clientacl / visibility / exec-inspect) upstream transports now set `ResponseHeaderTimeout: 30s`. A Docker daemon that accepts a connection but never sends response headers can no longer pin a goroutine until context cancellation. Streaming endpoints send headers promptly and hijacked attach/exec-start connections bypass the pooled transport, so long-lived responses are unaffected.

## [0.8.0] - 2026-05-14

### Added

- Added per-profile rollout modes via `clients.profiles[*].mode: enforce|warn|audit`. The default `enforce` preserves the existing default-deny behavior — a denied request returns `403`. `warn` and `audit` let an operator stage a tighter policy without breaking callers: every deny gate (filter rules + the request-body inspectors, ownership label isolation, client-ACL label policy, and the three rate-limit / concurrency / priority throttle gates) consults `meta.RolloutMode`. In `warn` / `audit` the request is still served upstream, the structured audit record carries `decision=would_deny`, and the deny / throttle counters fire either way with a new `mode` label so dashboards can compare blocked vs. would-have-been-blocked volume side by side. Pre-auth admission gates (CIDR allowlist, identity-lookup failures) stay `enforce` regardless of the profile's mode — those are unsafe to relax. Add the field to one profile to dry-run a change; flip back to `enforce` once the would-deny rate is what you expect.
- Added an opt-in `POST <admin.path>` (default `/admin/validate`) endpoint that accepts a candidate YAML config in the request body, runs the same parse/validate/compile pipeline as the offline `sockguard validate` command, and returns a structured JSON report (`{"ok": bool, "rules": int, "profiles": int, "compat_active": bool, "errors": [...]?}`). The endpoint is disabled by default (`admin.enabled: false`); when enabled it rides the main listener and inherits the listener's CIDR allowlist, mTLS posture, and per-profile rate-limit / concurrency caps. The handler hard-caps request bodies at `admin.max_body_bytes` (default 512 KiB), returns `405` with `Allow: POST` on non-POST methods, `413` on oversize bodies, `422` with the validation errors on a failing candidate, and `200` on success. Running policy is never mutated. Useful as a CI gate (`curl --data-binary @candidate.yaml http://sockguard/admin/validate`) before promoting a config to production. Companion `config.LoadBytes` helper parses YAML bytes without applying `SOCKGUARD_*` env overlays so the verdict reflects exactly what was submitted.
- Added `admin.path` / `admin.max_body_bytes` config validation: `path` must start with `/` and must not collide with `health.path` or `metrics.path` when those endpoints are also enabled; `max_body_bytes` must be `> 0`.
- Added opt-in hot reload of policy at runtime. When `reload.enabled: true`, sockguard watches the loaded config file via `fsnotify` (Linux inotify / macOS kqueue) and also reloads on `SIGHUP`. Filesystem events are debounced (`reload.debounce_ms`, default `250`) so a single editor save — which commonly emits a burst of chmod/write/rename/create events — collapses into one reload. The reload pipeline parses the new file, applies the same Tecnativa-compat expansion the startup path uses, runs the full validator + rule compiler, and atomically swaps the running handler chain on success. On any failure the running policy is preserved and the failure is logged. A rebuild that would mutate an **immutable** field — `listen.*`, `upstream.socket`, `log.*`, `health.*`, `metrics.*`, `admin.*`, or the `policy_bundle` trust material (`enabled`, `allowed_signing_keys`, `allowed_keyless`, `require_rekor_inclusion`, `verify_timeout`) — is refused (those fields are bound to long-lived sockets, goroutines, or trust roots that cannot be replaced without a process restart). `policy_bundle.signature_path` stays mutable so an operator can re-sign the same YAML without a restart. Two new metrics surface the outcome: `sockguard_config_reload_total{result="ok|reject_load|reject_validation|reject_immutable|reject_signature"}` counter, and a `sockguard_config_reload_last_success_timestamp_seconds` gauge that is omitted until the first successful reload. SIGHUP behavior changes when `reload.enabled` is true: previously SIGHUP terminated sockguard (Go's default action for unhandled SIGHUP); with reload enabled, SIGHUP triggers a reload and never terminates the process. Default is `reload.enabled: false` for backward compatibility.
- Added policy versioning. The proxy maintains a monotonic generation counter that ticks once at startup and once per successful hot reload; the counter is published two ways. `GET <admin.policy_version_path>` (default `/admin/policy/version`) returns a JSON snapshot — `{"version": int, "loaded_at": RFC3339, "rules": int, "profiles": int, "compat_active": bool, "source": "startup"|"reload", "config_sha256": hex, "bundle_source": string?, "bundle_signer": string?, "bundle_digest": hex?}` — and a new `sockguard_policy_version` Prometheus gauge mirrors the same counter for scrape-side monitoring. The endpoint is opt-in via `admin.enabled: true` (it shares the admin layer with `POST /admin/validate` and inherits the same listener CIDR allowlist, mTLS, and rate-limit posture). The version only ticks on a successful apply, so a stable value across two scrapes means the running policy genuinely did not move — useful for confirming that an operator-issued config change actually took effect. `config_sha256` is a SHA-256 of the effective config's JSON encoding so two snapshots with the same version (always equal) but different content hashes flag a config-drift bug; the field is best-effort and may be empty if the encoder fails. The `bundle_*` fields are stamped only when `policy_bundle.enabled: true` and let an operator confirm exactly who signed the running policy (`keyed:<spki-fingerprint>` or `keyless:<issuer>:<san>`) plus the SHA-256 digest of the verified YAML. Non-GET methods on the endpoint return `405 Allow: GET`; querying before the first publish returns `503`. Path is validated at config load: must start with `/` and must not collide with `admin.path`, `health.path`, or `metrics.path`.
- Added an optional dedicated admin listener. When `admin.listen.socket` or `admin.listen.address` is configured, the admin endpoints (`POST <admin.path>` and `GET <admin.policy_version_path>`) move to a separate `http.Server` bound to that address — the main Docker-API listener never sees admin traffic, and admin traffic never traverses the Docker-API filter, rate-limit, or client-ACL chain. The dedicated listener supports the same posture as `listen.*`: unix socket (hardened `0600` mode), loopback or TLS-protected TCP (with `admin.listen.tls.cert_file`/`key_file`/`client_ca_file` plus the existing CN/DNS/IP/URI/SPIFFE/SHA-256 SPKI client-identity selectors), or non-loopback plaintext TCP behind an explicit `admin.listen.insecure_allow_plain_tcp=true` opt-in. Validation rejects partial TLS configs, mismatched socket modes, and admin/main address collisions before the proxy starts taking traffic. When `admin.listen` is unset, the existing in-band behavior (admin endpoints share the main listener and inherit its CIDR allowlist, mTLS, and rate-limit posture) is preserved. The admin `http.Server` runs with explicit 30s `ReadTimeout`/`WriteTimeout` since admin endpoints never stream, and unknown paths on the dedicated listener return `404` rather than falling through to the Docker-API filter. An admin Serve failure is treated as fatal: the process exits with a wrapped `admin server error` so operators who opted into a dedicated control plane never silently lose it. The `admin.*` block (including `admin.listen.*`) remains immutable across hot reload — restart is required to change which listener admin rides.
- Added signed policy bundles. When `policy_bundle.enabled: true`, sockguard treats the on-disk YAML config as untrusted until a cosign sigstore bundle at `policy_bundle.signature_path` confirms it. Operators sign the YAML with `cosign sign-blob --bundle <out.bundle> <cfg.yaml>` and point sockguard at the resulting `<out.bundle>`. Trust paths reuse the same sigstore-go stack already powering image trust: `policy_bundle.allowed_signing_keys[]` holds PEM-encoded ECDSA / RSA / ed25519 public keys for keyed verification, `policy_bundle.allowed_keyless[]` holds `(issuer, subject_pattern)` constraints for Fulcio keyless verification, and `policy_bundle.require_rekor_inclusion` (default `true`) demands a transparency-log entry for keyless paths. Verification runs at startup before any rule compiles — a missing, malformed, or wrong-key bundle aborts the process with a wrapped `policy bundle:` error — and again on every hot reload, where a signature failure rejects the reload with the `reject_signature` reason in `sockguard_config_reload_total` and never touches the running policy. The verified signer fingerprint or identity and the YAML's SHA-256 digest are stamped onto the policy-version snapshot's `bundle_signer` / `bundle_digest` / `bundle_source` fields so `GET /admin/policy/version` answers "who signed the policy I'm running, and over what bytes?". Trust material (`enabled`, `allowed_signing_keys`, `allowed_keyless`, `require_rekor_inclusion`, `verify_timeout`) is reload-immutable so a SIGHUP cannot silently widen the set of accepted signers; only `signature_path` is reload-mutable so an operator can re-sign without restart. Default is `policy_bundle.enabled: false`. Backed by `github.com/sigstore/sigstore-go` — no new external dependency.

### Added

- Added `request_body.container_create.allowed_device_requests` — a structured opt-in for `HostConfig.DeviceRequests` that lets operators allowlist specific device request drivers (e.g. nvidia, amd) with fine-grained capability and count controls, without granting the blanket `allow_device_requests: true` escape hatch. Each allowlist entry specifies a required `driver` field (case-insensitive exact match), an `allowed_capabilities` list of capability sets (each capability set in the request must be a subset of at least one allowlisted set), and an optional `max_count` bound (`-1` = all devices; request `Count: -1` is only permitted when `max_count` is also `-1`). Rules evaluate in declaration order — first match wins — and unmatched requests default to `cost: 1`, preserving prior semantics. Lets operators tax expensive Docker operations (image pull, build, exec) proportionally without lowering the base rate for every endpoint. Throttle audit records emitted by cost-weighted denials carry the `cost` attribute so operators can distinguish expensive-endpoint denials from base-rate denials. Validation is fail-closed at startup: empty paths, malformed globs, costs below `1`, costs exceeding effective burst, and empty method strings all reject the config.

Sockguard now stamps `POST /services/create`, `POST /services/*/update`, `POST /secrets/create`, and `POST /configs/create` in addition to the existing container/network/volume/build coverage, stamps service task templates so downstream tasks inherit the same owner label, injects owner-label filters into `/services`, `/tasks`, `/secrets`, and `/configs` list reads, and denies cross-owner access across containers, images, networks, volumes, services, tasks, secrets, and configs. This closes the remaining ownership gap for Docker resources that actually expose label-based ownership semantics.
- Hardened unix-socket listener permissions to owner-only `0600`. Sockguard no longer accepts arbitrary `listen.socket_mode` octal values for unix listeners, startup validation now rejects anything other than `0600`, the listener path itself fail-closes if validation is bypassed, and the built-in default plus benchmark config were updated to match. This closes the easy misconfiguration path where a too-broad mode plus umask math could leave the proxy socket readable or writable by unintended local users.
- Expanded named per-client policy profiles. `clients.profiles` still defines reusable rulesets with profile-specific request-body inspection settings, `clients.source_ip_profiles` still assign them by caller CIDR, and `clients.default_profile` still provides a fallback for unmatched callers, but `clients.client_certificate_profiles` now match the verified mTLS leaf certificate by `common_names`, `dns_names`, `ip_addresses`, `uri_sans`, and `spiffe_ids`, while the new `clients.unix_peer_profiles` map unix-socket callers by peer `uids`, `gids`, and `pids`. Different selector fields on one assignment are ANDed, entries within one field are ORed, `clients.client_certificate_profiles` still require mutual TLS, and `clients.unix_peer_profiles` require `listen.socket`. The root `rules` plus root `request_body` remain the fallback policy when no profile is selected, access logs still record the selected profile, and `sockguard validate` now checks the richer selector shapes too.
- Added response filtering on successful Docker read calls. The proxy still enforces this in `httputil.ReverseProxy.ModifyResponse` with bounded 8 MiB body buffering and fails closed with a generic `502` if a protected JSON response cannot be sanitized safely, but the protected surface is now much broader: workload env arrays are redacted across container/service/task/plugin reads; host-path-bearing mount and device metadata are redacted across container/volume/task/service/plugin/system-usage reads; network/swarm/node topology is redacted across container/network/service/task/node/swarm/info/system-usage reads; and the new `response.redact_sensitive_data` / `SOCKGUARD_RESPONSE_REDACT_SENSITIVE_DATA` default-on toggle redacts config payload material, service secret/config references, plugin env values, swarm join/unlock and CA material, and node/swarm TLS metadata.
- Expanded read-side visibility control. `response.visible_resource_labels` and `clients.profiles[].response.visible_resource_labels` now inject Docker label selectors into service/task/secret/config/node lists in addition to the existing container/image/network/volume/event coverage, hide hidden inspect/log-style reads for those resource families behind `404`, hide `GET /swarm` when its labels do not match, and apply additively with selected client profiles.
- Completed request-aware enforcement for the remaining non-Swarm high-risk write paths. Sockguard now inspects `POST /containers/*/exec` bodies against an argv allowlist plus privileged/root-user toggles, re-inspects `POST /exec/*/start` via upstream `GET /exec/{id}/json` before execution, inspects `POST /images/create` query parameters to block `fromSrc` imports and constrain registries, and inspects `POST /build` to block remote contexts, `networkmode=host`, and Dockerfiles containing `RUN` instructions unless those behaviors are explicitly allowed. `/build` inspection replays the request body from a temp file so local tar contexts still reach Docker unchanged after policy checks.
- Capped request body reads at 1 MiB (`maxContainerCreateBodyBytes` and `maxOwnershipBodyBytes`) in the container-create inspection path (`internal/filter/container_create.go`) and the ownership mutation path (`internal/ownership/middleware.go`). An allowlisted client can no longer OOM the proxy by posting a multi-GB JSON body to `/containers/create`, `/networks/create`, or `/volumes/create`; an over-limit body short-circuits with a policy deny reason or error before the JSON decode runs.
- Added a singleflight + 10-second TTL cache in front of the client ACL `/containers/json` resolver (`internal/clientacl/cache.go`). Before, every inbound request from an allowed CIDR fired a fresh upstream Docker API call to map source IP → caller container; a burst of N concurrent requests amplified into N upstream calls, turning one allowlisted client into a steady source of Docker-daemon load. Concurrent misses for the same IP now coalesce into one upstream call, successful lookups are reused for up to 10 s, and the cache is bounded to 256 entries with a size-aware scrub-then-evict path. Errors are never cached so transient upstream recovery still works on the next caller.
- Switched `ownership.mutateJSONBody` to `json.NewDecoder(...).UseNumber()` so Docker container-create fields above 2^53 — `Memory`, `MemorySwap`, `PidsLimit`, `NanoCpus` — round-trip their exact digits through the Labels-injection rewrite. The default `map[string]any` decode silently coerced every JSON number to `float64` and truncated large integers on the re-encode pass.

The new setup escalates coverage across four tiers, matrix-parallelized so every tier's wall time is near its per-fuzzer budget regardless of how many fuzzers we ship:

Upload retention 180 days so a regression found by a monthly run stays recoverable long enough to turn into a committed seed.
