## Installation

### Docker Compose (recommended)

```yaml filename="docker-compose.yml"
services:
  sockguard:
    image: codeswhat/sockguard:latest
    restart: unless-stopped
    read_only: true
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
    group_add:
      - "${DOCKER_SOCK_GID:?set to the GID of /var/run/docker.sock}"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
      - ./sockguard.yaml:/etc/sockguard/sockguard.yaml:ro
      - sockguard-socket:/var/run/sockguard
    environment:
      - SOCKGUARD_LISTEN_SOCKET=/var/run/sockguard/sockguard.sock

volumes:
  sockguard-socket:
```

### Docker Run

```bash
docker run -d \
  --name sockguard \
  --read-only \
  --cap-drop=ALL \
  --security-opt no-new-privileges:true \
  --group-add <docker-socket-gid> \
  -v /var/run/docker.sock:/var/run/docker.sock:ro \
  -v ./sockguard.yaml:/etc/sockguard/sockguard.yaml:ro \
  -v sockguard-socket:/var/run/sockguard \
  -e SOCKGUARD_LISTEN_SOCKET=/var/run/sockguard/sockguard.sock \
  codeswhat/sockguard:latest
```

Sockguard runs as UID 65532 (Chainguard `nonroot`) inside the container.
Set `DOCKER_SOCK_GID` before starting Compose (`export DOCKER_SOCK_GID=$(stat -c '%g' /var/run/docker.sock)` on Linux; use `stat -f '%g'` on macOS), or replace `<docker-socket-gid>` in the `docker run` command with that numeric value. The hardening knobs that matter in practice are
`--read-only`, `--cap-drop=ALL`, `--security-opt no-new-privileges:true`, and
your runtime's seccomp/AppArmor/SELinux defaults.

The filtered socket and its named-volume directory are owner-only and owned by UID/GID 65532. A non-root consumer of that socket must also use UID 65532; root consumers can connect as well. If an application must keep another UID, run Sockguard with that matching UID against a pre-owned bind-mounted directory, set `listen.socket_mode: "0660"` with an explicit `listen.socket_gid` so a named group can reach the socket, or use an authenticated TCP listener. `0600` and `0660` are the only modes Sockguard accepts, and `0660` without `socket_gid` is rejected, so a group-shared socket is always a deliberate choice rather than a default.

### Helm

From v3.0.0, each stable release publishes its Helm chart to GitHub Container Registry as a signed OCI artifact. Chart version, app version and release tag are the same number, and the chart's default image reference is pinned to that release's multi-arch image digest.

```bash
helm install sockguard oci://ghcr.io/codeswhat/charts/sockguard --version 3.0.0
```

Replace `3.0.0` with the release you want. Release candidates and maintenance patches (for example v2.4.x) do not publish a chart; for those, install from the `chart/sockguard` directory of the matching tag. The chart does not grant Docker socket access beyond what its values configure, so review `helm show values oci://ghcr.io/codeswhat/charts/sockguard --version 3.0.0` and set an explicit policy before installing. To check the chart's signature first, see [Verifying the Helm chart](/verification#verifying-the-helm-chart).

### Binary

Download from [GitHub Releases](https://github.com/CodesWhat/sockguard/releases):

```bash
sockguard serve -c /etc/sockguard/sockguard.yaml
```

This guide uses a unix socket because it is the simplest secure deployment. If you expose Sockguard on non-loopback TCP, configure `listen.tls` for mutual TLS. Plaintext remote TCP requires the two-flag legacy opt-in — both `SOCKGUARD_LISTEN_INSECURE_ALLOW_PLAIN_TCP=true` and `SOCKGUARD_LISTEN_INSECURE_ALLOW_UNAUTHENTICATED_CLIENTS=true`.

### Published v3 release candidate

[v3.0.0-rc.8](https://github.com/CodesWhat/sockguard/releases/tag/v3.0.0-rc.8)
is available for testing. Select `ghcr.io/codeswhat/sockguard:3.0.0-rc.8`
explicitly, download its platform binary from that release, or install it with Go 1.27:

```bash
go install github.com/codeswhat/sockguard/v3/app/cmd/sockguard@v3.0.0-rc.8
```

Go consumers must use `/v3` imports; v2 candidate tags retain `/v2`. See the
[v3 migration guidance](/migration#from-sockguard-v2-to-v3-release-candidate)
before validating an existing configuration. The stable installation channels
above serve v2.4.9. The candidate has its own validation and 14-day bake
window. rc.8 restarts the bake, so GA is no earlier than 14 days after rc.8
publishes.
Candidate-only behavior fixes restart the window.

## Connecting Your Apps

Point your Docker consumers at the proxy socket instead of `docker.sock`:

```yaml
services:
  traefik:
    volumes:
      - sockguard-socket:/var/run/sockguard:ro
    environment:
      - DOCKER_HOST=unix:///var/run/sockguard/sockguard.sock

  drydock:
    volumes:
      - sockguard-socket:/var/run/sockguard:ro
    environment:
      - DD_WATCHER_LOCAL_SOCKET=/var/run/sockguard/sockguard.sock
```

## CLI Commands

```bash
# Start the proxy (default command)
sockguard serve

# Start with a signed policy and separate pinned trust
sockguard serve --config /etc/sockguard/sockguard.yaml --policy-bundle-trust-config /etc/sockguard/policy-bundle-trust.yaml

# Validate configuration and print the compiled rule table
sockguard validate -c /etc/sockguard/sockguard.yaml

# Same, but exit non-zero if the file has unrecognized keys (CI gate)
sockguard validate --strict -c /etc/sockguard/sockguard.yaml

# Offline dry-run: evaluate a single request against the rules,
# show which rule fires and why, without starting the proxy.
sockguard match -c /etc/sockguard/sockguard.yaml \
  -X GET --path /v1.45/containers/json

# Suggest allow rules from warn or audit access-log lines (stdout only)
sockguard policy suggest --from /var/log/sockguard/access.jsonl

# Runtime self-check: is the upstream daemon answering, is this
# sockguard's own health endpoint up, does the TLS material load
sockguard verify -c /etc/sockguard/sockguard.yaml

# Print version
sockguard version
```

`sockguard match` reads the same config, applies the same path
normalization as the running proxy, and reports the decision in
text (default) or JSON (`-o json`). Use it to sanity-check a
ruleset before any traffic hits the proxy.

To see what a client profile would do, add `--profile NAME`, or `--source-ip IP`
to let `match` pick the profile the proxy would pick (the first matching
`clients.source_ip_profiles` entry, then `clients.default_profile`). The output
names the profile and how it was selected, its rollout mode, the effective
ownership scope, and the configured response redaction and visibility lists.
Everything beyond the rule decision is read from the config, not from a running
daemon. Each run ends with a `Not inspected` list (`not_inspected` in JSON):
the request body, live resources, and any client certificate or unix peer
assignments that would select a profile before source IP.

To check a request body too, add `--body-file PATH` (or `--body-file -` to read
stdin). `match` runs the same request-body inspectors the proxy runs (container
create, exec create, service, build, image pull, volume and network writes, and
the rest) on that file, for the selected profile or the root policy, and reports
the verdict: `allow`, or `deny` with the inspector's reason and reason code
(`request_body_policy_denied`, `request_body_too_large`, and so on). The body
verdict joins the rule decision, so a body deny turns an allowed request into a
deny, and under a `warn` or `audit` profile it passes through the way the proxy
would. Three cases report no verdict: the rules denied the request first
(`skipped`, since the proxy only reads the body of an allowed request), no
inspector covers that method and path (`not_inspected`, and the file is never
read), and `POST /exec/{id}/start` (`not_inspected`, since its check is a lookup
of the exec instance on the daemon). Nothing is looked up on a daemon. A
`Not evaluated` line lists each check that needs one: the exec target's
protection label, and the Docker or Podman and cgroup-version gates on container
create, build and image push, which run with their offline defaults.
Ownership and visibility are still read from the config only. An unreadable
file fails the command.

`sockguard verify` is the runtime counterpart to `sockguard
validate`. Where validate is an offline check on a config file,
verify loads the config the way `serve` does (flags, environment,
file) and then checks that the things it names are reachable right
now. It runs five checks and prints one line each:

| Check | What it does |
|-------|--------------|
| `config` | Loads and validates the effective config, without touching the filesystem paths it names. |
| `upstream` | Builds the upstream endpoints (loading their TLS material), runs the same reachability probe `serve` runs at startup, asks the Docker API through the same readiness probe `/health` uses, and resolves the engine flavor. |
| `listener` | Issues `GET <health.path>` against each configured listener. |
| `tls` | Opens the cert, key, and client CA that each mutual-TLS listener names — the filesystem half of validation that `POST /admin/validate` deliberately skips. |
| `image-trust` | Reports whether image trust is configured and, when it uses keyless identities, whether the Sigstore trust root loads. |

Each check reports `ok`, `fail`, or `skip`. A `skip` is a check
that does not apply to this deployment — an opt-in feature that is
off, a listener that is not running — and never changes the exit
code; any `fail` exits non-zero, so verify works as a container
healthcheck or a deploy gate. Add `--json` for a machine-readable
report with the same five checks in the same order. `--listen-socket`
and `--upstream-socket` override the config the same way they do on
`serve`.

Verify does not need the proxy to be running: with no listener up,
the `listener` check skips and everything else still runs, so it is
also a pre-flight check on a host before the first start.

Signed-policy mode requires the candidate and bootstrap trust config to be
different files, including after symlink or hardlink resolution. The trust
file uses `policy_bundle.enabled`, signing identities, Rekor posture, and the
verification timeout. The signed candidate carries
`policy_bundle.signature_path`. Rule-generating Tecnativa variables cannot be
combined with this mode; migrate those grants to YAML before signing. See
[Signed Policy Bundles](/configuration#signed-policy-bundles) for the complete
layout.

### Suggesting rules from warn and audit traffic

Run a profile in `warn` or `audit` rollout, collect the JSON access log, then
let sockguard draft the rules that would have let that traffic through:

```bash
sockguard policy suggest --from /var/log/sockguard/access.jsonl > suggested-rules.yaml
```

Use `--from -` to read stdin. The command reads only `request_would_deny`
lines, groups them by profile, method and normalized path, and prints a YAML
`rules:` snippet to stdout. Only would-denies with `reason_code:
no_matching_allow_rule` become rules. A would-deny from an explicit deny rule, or
from body inspection, ownership, visibility or rate limiting, is counted in a
header comment and the summary but never suggested, because an allow rule would
override a deliberate deny or couldn't fix it. Each rule shows the profile the
traffic came from; rules from a named profile belong under that profile, not the
root `rules:` list. It never writes a config file and nothing it prints is
active until you copy it in, so treat every rule as a suggestion that needs
review. Each rule carries a comment saying so, and write methods are flagged.

What it will and won't include:

- Only the method and the normalized path are read. Query strings, headers,
  bodies, client addresses and request IDs never reach the output.
- Segments that are 12 to 64 lowercase hex characters (container, exec and
  network IDs) become `*`, but only right after a literal resource segment
  (`/containers/<id>/logs`). A path that starts with an ID, or has two IDs in
  a row, is skipped, so one odd request can't turn into an allow-everything
  rule such as `GET /*`. Names stay literal, since a name can't be told from
  a path word.
- A path containing glob characters, `..`, encoded bytes or anything outside
  letters, digits and `-_.~:` is skipped and counted, never emitted.
- Input is bounded: lines over 64 KiB are skipped, reading stops at 1,000,000
  lines, and at most 500 distinct rules are printed.
- The snippet is compiled with the same rule compiler `serve` uses before it
  is printed. A snippet that fails to compile is an error, not output.

The suggested rules are plain `allow` rules with no body or query constraints.
Tighten them (`match.query`, request-body policy, ownership) before relying on
them, and place them before your final deny. A summary line goes to stderr.
