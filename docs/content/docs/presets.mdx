Sockguard ships with ready-made config presets for common Docker consumers. All presets are bundled in the container image at `/etc/sockguard/`.

## Drydock (`drydock.yaml`)

Optimized for the [drydock](https://github.com/CodesWhat/drydock) container update manager.

**Use for:** drydock, or any container updater that needs lifecycle control + image pull.

```yaml
# Allows: container read
# Allows: container lifecycle (start, stop, restart, kill, rename, update, wait, create, remove)
# Allows: image read, pull, remove
# Allows: network read + connect, volume read, distribution, Swarm service reads
# Denies: exec, build, swarm writes, secrets, plugins, raw archive/export/logs/attach streams
# container-create bodies are inspected by default — add host bind-mount sources to
# request_body.container_create.allowed_bind_mounts if your updates require them.
# image pulls are inspected too; this preset explicitly allows arbitrary registries
# while still denying image imports via fromSrc
# container updates are inspected; restart-policy/resource/device/capability changes
# stay denied unless you explicitly allow them under request_body.container_update
# container removal permits drydock's force-removal recovery path but keeps
# anonymous-volume and legacy-link deletion denied
# the stock "runc" runtime is allowlisted (request_body.container_create.allowed_runtimes)
# because drydock recreates containers from their inspect spec, which usually carries an
# explicit HostConfig.Runtime — without it every update would 403 at /containers/create
# Three response redactions are off: redact_mount_paths, redact_container_env
# and redact_network_topology. redact_sensitive_data stays on, at its default.
# Drydock recreates a container from its own
# inspect payload, so a "<redacted>" placeholder would be forwarded straight into
# POST /containers/create and dockerd would reject it. The four drydock-with-*
# presets inherit this; re-enable them only if the consumer never replays inspect
# output back into a create body.
```

## Drydock with Self-Update (`drydock-with-selfupdate.yaml`)

Extends the drydock preset with the exec paths required for drydock's self-update
finalize flow. The finalize step runs a short-lived `docker exec` inside the new
container to POST a completion callback to drydock's internal API.

**Use for:** drydock deployments where the sockguard proxy is in the self-update
path and you need the finalize callback to complete cleanly.

```yaml
# Extends drydock.yaml with:
# Allows: POST /containers/{id}/exec, POST /exec/{id}/start, GET /exec/{id}/json
# Allows: container-create bodies that bind-mount /var/run/docker.sock
#         (request_body.container_create.allowed_bind_mounts, which drydock.yaml
#         leaves empty). The socket-mode recreate needs it; set it back to [] if
#         drydock reaches the daemon over TCP. This is the largest security
#         difference between the two presets.
# Exec body inspection: allow_privileged=false, allow_root_user=true
# (drydock's exec create sets no User field, and sockguard treats an empty
# User as root, so allow_root_user must be true or the finalize exec is
# denied before allowed_commands is ever checked)
# allowed_commands pins exec to the single finalize entrypoint argv, so the
# root-user allowance is safe: only that exact command can run
# allowed_env_vars pins exec Env to the six DD_SELF_UPDATE_* names. Without it
# the argv pin is not enough on its own: NODE_OPTIONS could --require arbitrary
# code under the pinned node command
# allowed_env_values pins the finalize callback to Drydock's loopback URL at
# port 3000; update the exact value if you configure a different server port
```

Without this preset (using drydock.yaml), the self-update still completes — the
old container is renamed, the new one starts — but the finalize callback exec is
denied and drydock logs the failure. Use this preset to get a clean finalize.

## Drydock with Compose (`drydock-with-compose.yaml`)

Extends the drydock preset with the network and volume lifecycle a
`docker compose` stack needs — the same gap `portwing-with-compose.yaml`
closes for Portwing.

**Use for:** drydock deployments that recreate a `docker-compose.yml` stack
through this proxy, not just a single standalone container.

```yaml
# Extends drydock.yaml with:
# Allows: POST /networks/create, DELETE /networks/*, POST /networks/*/disconnect
#         POST /volumes/create, DELETE /volumes/*
# (POST /networks/*/connect is already allowed by drydock.yaml — untouched)
# Body inspection for the new endpoints reuses drydock.yaml's existing
# network/volume create guardrails (deny custom drivers/driver opts by default)
# Container removal additionally permits Compose's force and anonymous-volume
# cleanup controls; legacy link deletion stays denied
# Still denied: /build, /session, /grpc. `docker compose build` / `up --build`
# with default settings never calls POST /build at all — it drives dockerd's
# embedded BuildKit over the hijacked, unversioned /session and /grpc streams
# instead, both denied here. Use drydock-with-mediated-build.yaml if you want
# `--build` support with BuildKit's default (no env var) transport, fully
# mediated (issue #185) rather than opened wholesale. Use drydock-with-build.yaml
# instead if you specifically want the CLASSIC builder (POST /build only,
# requires DOCKER_BUILDKIT=0 in the client). See the Compose/BuildKit
# Transport section of the security model docs for the full breakdown.
# Compose-Spec post_start hooks are also still denied: they run through exec
# (POST /containers/{id}/exec, POST /exec/{id}/start), which the catch-all
# blocks, so drydock's PostStartExecutor fails the deploy loudly rather than
# skipping the hook. Add a pinned allowed_commands entry (modeled on
# drydock-with-selfupdate.yaml) rather than a blanket exec allow if you need it.
# Self-update finalize exec is still denied, same caveat as drydock.yaml;
# combine with drydock-with-selfupdate.yaml by hand if you need both
```

## Drydock with Build (`drydock-with-build.yaml`)

Extends `drydock-with-compose.yaml` with **classic builder only** support for
`docker compose build` / `up --build`, for deployments that need Sockguard to
inspect build requests rather than blanket-deny them.

**Use for:** drydock-managed compose stacks that build images locally instead
of only pulling pre-built ones — with the caveat that the client must run with
`DOCKER_BUILDKIT=0` set (see below).

```yaml
# Extends drydock-with-compose.yaml with:
# Allows: POST /build — classic builder only, request_body.build left at its
#         secure defaults (allow_remote_context/allow_host_network/
#         allow_run_instructions all false)
# Still denies: /session, /grpc, and any moby.buildkit.v1.Control method path
# — this preset does not open either endpoint, no insecure_accept_opaque_
# buildkit_tunnels acknowledgment (now deprecated) and no request_body.buildkit
# mediation policy. THIS FAILURE IS INTENTIONAL: modern Buildx defaults to
# BuildKit, so a default `docker compose build` against this preset still
# fails with a /session or /grpc denial. Set DOCKER_BUILDKIT=0 in the client
# environment to fall back to the classic builder this preset actually
# supports, or use drydock-with-mediated-build.yaml for the fully-mediated
# BuildKit alternative.
```

## Drydock with Mediated Build (`drydock-with-mediated-build.yaml`)

Extends `drydock-with-compose.yaml` with **mediated BuildKit** support —
`docker compose build` / `up --build` run with BuildKit enabled (the Docker
CLI default, no `DOCKER_BUILDKIT=0` needed). Sockguard terminates the
`POST /session`/`POST /grpc` tunnel as h2c and inspects every gRPC message
crossing it (issue #185) instead of admitting the tunnel wholesale.

**Use for:** drydock-managed compose stacks that build images locally with
BuildKit's default transport, where you want the same per-message inspection
this preset's classic-builder sibling gets for `/build`.

```yaml
# Extends drydock-with-compose.yaml with:
# Allows: POST /session, POST /grpc — mediated only; request_body.buildkit
#         admits Control.Solve (an "image"-typed exporter, no push registry
#         allowlisted), Control.Info/ListWorkers/Status (worker metadata and
#         ref-owned build progress), and Session.FileSync (REQUIRED — this is
#         how the Dockerfile and context reach buildkitd; still subject to
#         the same RUN-instruction hold-and-inspect scan classic /build gets,
#         since allow_run_instructions stays false)
# request_body.build's three flags stay at their secure defaults
# (allow_remote_context/allow_host_network/allow_run_instructions all false),
# reused verbatim for Solve's own entitlement/frontend checks
# Left denied by default (widen only if you need it): session.auth (base-image
# pulls needing registry auth — exact realm/scope match, no generic default
# covers arbitrary Dockerfiles), session.secrets/ssh (RUN --mount=type=secret/
# ssh), session.file_send/upload (local/tar export, remote/stdin context)
# Still denies: classic POST /build (use drydock-with-build.yaml instead) and
# the literal /moby.buildkit.v1.Control/<Method> probe path (no h2c upgrade
# for any mediator to terminate)
# insecure_accept_opaque_buildkit_tunnels is NOT set — it is deprecated and
# mutually exclusive with request_body.buildkit
```

## Portwing (`portwing.yaml`)

Optimized for the [Portwing](https://github.com/CodesWhat/portwing) Docker agent.

**Use for:** Portwing in the tri-tool topology (sockguard → Portwing → drydock), or
any remote Docker agent that needs lifecycle control, image pull, and event streaming.

```yaml
# Allows: container read (list, inspect, stats, top, changes, logs)
# Allows: container lifecycle (start, stop, restart, kill, rename, update, wait, create, remove)
# Container removal permits Portwing's force option; anonymous-volume and
# legacy-link deletion stay denied
# Allows: image read, pull, remove
# Allows: network read, network connect (Aliases-only endpoint config, so drydock
#         can re-attach extra networks on recreate), volume read, distribution,
#         Swarm service reads
# Denies: exec, build, swarm writes, secrets, plugins, raw archive/export/attach streams
# insecure_allow_read_exfiltration=true — required because GET /containers/*/logs and
# GET /containers/*/top are allowed (Portwing's GetContainerLogs() and process view); logs can
# carry secrets and top returns process command lines. Drop those rules and this
# flag to harden. top requests carrying ps_args are denied, because ps_args reaches the
# host's ps and its `e` flag prints each process's environment. /containers/*/archive, /export, /attach stay denied (bulk-exfil paths).
# Response redactions disabled (redact_mount_paths=false, redact_container_env=false,
# redact_network_topology=false) — required for drydock passthrough topology so
# inspect data forwarded to drydock is not corrupted by "<redacted>" placeholders
# Standalone operators not paired with drydock can re-enable all three redactions
# deny_verbosity: verbose returns detailed denial reasons to the caller.
# That is safe here because the consumer is the trusted Portwing agent or drydock
# controller. The runner and CIS presets use deny_verbosity: minimal instead.
```

## Portwing with Exec (`portwing-with-exec.yaml`)

Extends the Portwing preset with exec support for interactive terminal access through
the Portwing agent, e.g. terminal-over-websocket or drydock-driven exec in edge mode.

**Use for:** Portwing deployments where exec sessions are needed (interactive terminals,
drydock edge mode exec calls).

```yaml
# Extends portwing.yaml with:
# Allows: POST /containers/{id}/exec, POST /exec/{id}/start,
#         POST /exec/{id}/resize, GET /exec/{id}/json
# Exec body inspection: allow_privileged=false, allow_root_user=true
# (most container workloads run as root; set false + use allowed_commands for
# non-root or command-pinned deployments)
# insecure_allow_body_blind_writes=true — interactive exec can't be pinned to a fixed argv,
# so the body-blind-write guard is bypassed; the allow_privileged/allow_root_user layer still
# applies. insecure_allow_read_exfiltration=true is inherited from portwing.yaml for the
# GET /containers/*/logs rule (see the Portwing section above).
```

## Traefik (`traefik.yaml`)

Minimal read-only access for Traefik reverse proxy.

**Use for:** Traefik's Docker provider. The allowlist is source-verified against
Traefik v3.7.12; other reverse proxies need their own call-surface review.

```yaml
# Allows: GET container list + inspect, network/service/task lists, node inspect
#         (Swarm), events, ping, version
# Denies: everything else, including container archive/export/logs/attach
```

In Swarm mode, task discovery includes node inspection at `GET /nodes/*`.
Every allowed path is a named list or required inspect endpoint rather than a
`/containers/**` glob, so this preset does **not** set
`insecure_allow_read_exfiltration: true`. A client that genuinely needs
`GET /containers/*/logs` or `GET /containers/*/archive` has to add that rule
and the acknowledgment itself.

The preset sets `response.redact_network_topology: false` because Traefik routes to container IPs, so blanked addresses would leave it with nothing to route to.

## Portainer (`portainer.yaml`)

Full Docker API access for Portainer management UI.

**Use for:** Portainer with full management capabilities.

```yaml
# Allows: containers, images, networks, volumes, exec, build, swarm, plugins (full R/W)
# WARNING: This grants near-full Docker socket access
# Container, image, build, network, swarm, node, and plugin writes are inspected, but
# the preset sets insecure_allow_body_blind_writes: true and
# insecure_allow_read_exfiltration: true unconditionally, because Portainer runs
# arbitrary exec and proxies every read endpoint
# request_body.build is fully widened as well (allow_remote_context,
# allow_host_network and allow_run_instructions are all true), so POST /build is
# admitted without the RUN-instruction or remote-context checks the drydock and
# portwing build presets keep, and image_pull.allow_all_registries is true
```

Portainer's cleanup path uses force removal and anonymous-volume removal, so
both controls are enabled. Docker's legacy link-removal mode stays denied.

The preset sets `response.redact_mount_paths`, `redact_container_env`, and
`redact_network_topology` to `false`. Portainer's container Recreate inspects
the container and replays the result into container create, and it disconnects
networks by the inspected network ID. Network IDs are no longer redacted, but
with the default redactions env and binds would be lost on create. Keep these
off for Portainer.

With these off, Portainer sees env values (including secrets), host bind paths
and network addresses in inspect output. The preset already sets
`insecure_allow_read_exfiltration`, so this is mostly not new exposure.
Operators who don't use Recreate or Duplicate can turn the three redactions
back on.

## Watchtower (`watchtower.yaml`)

Covers both Watchtower forks: [nicholas-fedor/watchtower](https://github.com/nicholas-fedor/watchtower),
the maintained continuation, and the archived `containrrr/watchtower` (v1.7.1). The preset was checked
against both upstreams' container client code: the core recreate flow (list/inspect, force-remove,
create with copied network config, start, rename, exec lifecycle hooks, image pull/remove) is shared.
containrrr stops containers with `POST /containers/{id}/kill` and disconnects the default network
(`POST /networks/{id}/disconnect`, with `force`) after create, so the preset allows both and sets
`request_body.network.allow_disconnect_force: true`. Kill applies to any container, and forced disconnect
applies to any container on any network, unless owner labels are enabled. nicholas-fedor stops with `/stop` instead, and only
reads `GET /system/df` when its image disk-usage thresholds are set. That route is a commented-out rule
in the preset; uncomment it if you use those thresholds.

On cgroup v1 hosts (Synology, for example), a recreate replays `HostConfig.CgroupnsMode: "host"`, which
container create denies by default. The Watchtower, Drydock and Portwing presets carry a commented
`request_body.container_create.allow_host_cgroupns_on_cgroup_v1: true` line. Uncomment it on those hosts.
Sockguard reads `CgroupVersion` from the daemon's `GET /info` from every upstream endpoint (at startup,
then every 5 minutes and on upstream health changes, so no restart is needed after a migration), and allows `CgroupnsMode: "host"` only when all of them report `"1"`. On a cgroup v2 host, or
when `/info` can't be read, create still denies it. `ns:<path>` stays denied either way. Use the
unconditional `allow_host_cgroupns: true` only if you want host cgroup namespaces on a cgroup v2 daemon.

**Use for:** Watchtower v1.21.2 with lifecycle hooks and network-aware updates.

```yaml
# Allows: ping/info; container list, inspect, start, stop, kill, rename,
#         update, remove and create; image inspect, pull and remove;
#         lifecycle-hook exec; network connect and disconnect
# Denies: every unused container/image/network route, all volume and
#         distribution routes, read-exfiltration routes, build, swarm,
#         secrets, configs and plugins
```

Container create allows the stock `runc` runtime and rejects other explicit
runtimes. It also admits the copied endpoint addressing and optional
user-configured MAC that Watchtower preserves during recreation, without
allowing endpoint links, driver options, link-local IPs, or gateway priority.
Watchtower copies those four fields verbatim from the old container, so a
container that relies on legacy links, per-endpoint driver options, link-local
IPs or a custom gateway priority cannot be recreated through this preset. Open
the matching `endpoint_config` switch for that field alone rather than
`allow_endpoint_config`, which would also admit links and driver options.
Container update allows the restart-only request Watchtower uses to set
`Name: "no"`. This is a nicholas-fedor addition: containrrr/watchtower never
called `POST /containers/{id}/update` at all, so the rule is simply unused
against the original image rather than unsafe. Moby serializes the embedded
`Resources` fields at their zero values in that request, which the daemon
treats as no-ops; nonzero resource, privilege, device and capability updates
remain denied, matching the fact that no code path in either upstream submits
real resource limits through this route. Image list is
explicitly denied before the registry-qualified image-inspect rule. The preset
permits Watchtower's force-removal path and optional anonymous-volume cleanup,
while legacy link removal stays denied. It keeps
`insecure_allow_body_blind_writes: true` for arbitrary lifecycle hooks and
allows an empty exec user because Watchtower uses the container's configured
user, but it no longer needs `insecure_allow_read_exfiltration: true`. Like the
drydock presets it also turns off the mount-path, container-env and
network-topology redactions, because Watchtower recreates containers from the
inspect payload it just read; `redact_sensitive_data` stays on.

## Homarr (`homarr.yaml`)

Optimized for [Homarr](https://homarr.dev) dashboard with container management.

**Use for:** Homarr with start/stop/restart/remove controls enabled.

```yaml
# Allows: GET container list + inspect + stats + logs
# Allows: POST start/stop/restart and DELETE container
# Denies: every other Docker API route, including all image routes
```

Homarr v1.76.2 uses container logs, so this preset still sets
`insecure_allow_read_exfiltration: true`. Logs are the only exfiltration route
it allows; container archive, export and attach routes and image tarball routes
stay denied. Its dockerode call is `container.remove()` with no options, so the
preset allows only bare container removal; `force`, anonymous-volume deletion,
and legacy link deletion stay denied.

## Dozzle (`dozzle.yaml`)

Least-privilege access for [Dozzle](https://dozzle.dev)'s default read-only view.

**Use for:** Dozzle with container list, live logs, stats and events, and nothing else.

```yaml
# Allows: GET /_ping, /version, /info, /events
# Allows: GET container list + inspect + stats + logs
# Denies: every other Docker API route
```

Derived from Dozzle v11.5.0 (`internal/container/docker/client.go`). Dozzle's
purpose is reading logs, so this preset sets `insecure_allow_read_exfiltration: true`.
Logs are the only exfiltration route it allows; archive, export, attach and top
stay denied. Network topology redaction is off (`redact_network_topology: false`):
Dozzle parses every container's network addresses while listing, and the
redaction placeholder makes it exit with "Could not connect to any Docker
Engine". Mount paths and env stay redacted, so the container details show
placeholders for host paths. Container actions (`DOZZLE_ENABLE_ACTIONS`) and the shell
(`DOZZLE_ENABLE_SHELL`) are not supported and sockguard refuses the calls they
make. Dozzle's volume and disk-size readout (`GET /system/df`) is denied and
Dozzle carries on without it. Swarm mode and agent mode are untested.

## Dozzle with Actions (`dozzle-with-actions.yaml`)

Extends the Dozzle preset with the buttons behind `DOZZLE_ENABLE_ACTIONS`.

**Use for:** Dozzle where operators start, stop and restart containers from the UI.

```yaml
# Extends dozzle.yaml with:
# Allows: POST /containers/{id}/start, /stop, /restart
# Denies: container remove, kill, rename, update, create, exec, image pulls,
#         prune and Dozzle's self-update
```

Dozzle's server route also accepts a `remove` action, but its UI only offers
start, stop and restart, so `DELETE /containers/{id}` stays denied. The same
flag also switches on Dozzle's image-update flow (pull, recreate, roll back),
the host prune buttons and its self-update. Those need container create and
remove, image pulls and prune, so they fail with a refusal under this preset.
Anyone who can open Dozzle's UI can restart every container it lists, so put
Dozzle behind its own authentication (`DOZZLE_AUTH_PROVIDER`).

## Dozzle with Shell (`dozzle-with-shell.yaml`)

Extends the Dozzle preset with the Shell tab behind `DOZZLE_ENABLE_SHELL`.

**Use for:** Dozzle where operators open a terminal in a container from the UI.

```yaml
# Extends dozzle.yaml with:
# Allows: POST /containers/{id}/exec, POST /exec/{id}/start,
#         POST /exec/{id}/resize
# request_body.exec:
#   allow_privileged: false
#   allow_root_user: true   # Dozzle sends an empty User, read as root
#   allowed_users: [""]     # only an unset User passes; explicit users are refused
#   allowed_commands:
#     - ["sh", "-c", "command -v bash >/dev/null 2>&1 && exec bash || exec sh"]
# Denies: any other exec command, container actions, the Attach tab, images
```

Dozzle sends the same argv for every shell session (`internal/web/terminal.go`
in v11.5.0), so the preset pins it with `allowed_commands`. Sockguard matches
the whole argv: any other command or a privileged exec is refused on create,
and exec start re-checks the stored command before it runs. The preset does
not set `insecure_allow_body_blind_writes`.

The pin limits what starts, not what a person types afterwards. Anyone who can
open the Shell tab has a shell in every container Dozzle lists. Dozzle's own
tab runs as the container's default user, but sockguard cannot pin the exec
User on its own (`allow_root_user` must be true because Dozzle sends an empty
User, read as root), so `allowed_users: [""]` pins it: a request with any
explicit User, root included, is refused on create and on the exec-start
re-check. On exec start Docker reports the container's configured user for an
unset User, and sockguard accepts that value as "unset", so the Shell tab works
on images that set `USER`. The shell then runs as the container's configured
user, which is still root for images that default to it. Treat the grant as a shell in every
container Dozzle lists, put Dozzle behind its own authentication and limit the
shell role. Containers labeled `com.sockguard.exec=deny` are always
refused, including the official sockguard image. The Attach tab
(`POST /containers/{id}/attach`) feeds stdin to the container's main process
and the exec allowlist does not cover it, so it stays denied and the tab fails
with a refusal. Dozzle never calls exec inspect, so `GET /exec/{id}/json` stays
denied.

## Diun (`diun.yaml`)

Minimal read-only access for [Diun](https://github.com/crazy-max/diun) (Docker Image Update Notifier).

**Use for:** Diun, or any tool that only needs to discover running containers and inspect images.

```yaml
# Allows: GET container list, image inspect, ping, version
# Denies: all other routes. Diun checks registries directly. Container
#         inspect is denied too; Diun's Docker provider never calls it
```

Image inspect is written `GET /images/**/json` rather than `/images/*/json`
because Docker registers the route as `/images/{name:.*}/json` and `{name:.*}`
spans slashes, so a registry-qualified image arrives as

`/**` can match zero segments, an earlier `GET /images/json` deny also keeps
the unused image-list call out of the surface. That is why this preset does
**not** set `insecure_allow_read_exfiltration: true`.

The preset leaves `response.redact_network_topology` at its default (on).
Redaction rewrites `NetworkSettings.Networks[*].IPAddress`, `Gateway`,
`GlobalIPv6Address`, `IPv6Gateway` and `MacAddress` to type-valid empty values,
and Network IDs and `NetworkMode` are not redacted, so Diun decodes the
container list without errors. Diun doesn't read container addresses. Set
`response.redact_network_topology: false` if you want them.

This preset intentionally sets `insecure_allow_read_exfiltration: true` for
container process monitoring on both API surfaces. Docker-compatible
`GET /containers/{id}/top` forwards caller-selected `ps_args` to the daemon
host's `ps`, and native `GET /libpod/containers/{id}/top` exposes the same
process-list class; both return command lines without response redaction. Every
other exfiltration-gated route remains denied by the narrow rules, including
native `GET /libpod/pods/{id}/top`, which carries the same global guard but is
not part of this preset's pod read surface. The flag is global rather than
per-rule, so anything you add to this preset later that the exfiltration
catalog covers, container logs being the obvious one, is admitted without a
fresh startup refusal to warn you. A monitoring consumer needs no custom
`ps_args` (the `e` flag prints each process's environment, undoing env
redaction), so any `top` request carrying `ps_args` is denied on both
surfaces. Point
`upstream.socket` at either a rootful
(`/run/podman/podman.sock`) or rootless (`$XDG_RUNTIME_DIR/podman/podman.sock`)
Podman socket; the rule set itself doesn't change.

## Using a Preset

Mount the preset as your config file:

```yaml
services:
  sockguard:
    image: codeswhat/sockguard:latest
    group_add:
      - "${DOCKER_SOCK_GID:?set to the GID of /var/run/docker.sock}"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
      - sockguard-socket:/var/run/sockguard
    environment:
      - SOCKGUARD_LISTEN_SOCKET=/var/run/sockguard/sockguard.sock
    command: ["serve", "-c", "/etc/sockguard/drydock.yaml"]
```

Neither addition is optional. No preset sets `listen.socket` and the default is
`listen.address: "127.0.0.1:2375"`, so without `SOCKGUARD_LISTEN_SOCKET` sockguard
binds container-local TCP and never writes into the volume the example mounts.
Sockguard also runs as UID 65532, so it can't open a stock `0660 root:docker`
socket without `group_add`.

All preset configs are bundled in the image at `/etc/sockguard/`. Three of the 25
files there aren't workload presets: `sockguard.yaml` is the default config the
container loads when no `-c` is given, and `discovery.yaml` and
`multi-listener.yaml` are covered in [Configuration](/configuration).

Presets that keep broad container/image read compatibility also carry explicit `insecure_allow_read_exfiltration: true` acknowledgements so they continue to validate honestly under the read-side export guardrail.
