title: Artifact Verification
description: Verify signatures and reproduce Sockguard Go binaries from pinned source and build inputs.
---

Every sockguard release is signed with [cosign](https://github.com/sigstore/cosign)
using GitHub Actions OIDC keyless signing. Before running a sockguard
image in production, verify it against the expected signing identity —
this is the only reliable way to be sure you're running a binary we
actually published.

## What cosign verifies

The `cosign verify` command below verifies the image signature:

- The image digest was signed by a workflow whose OIDC identity matches
  the release pipeline in this repo.
- The signature is present in Sigstore transparency metadata.
- The certificate chains to the expected GitHub Actions OIDC issuer.

The release pipeline also requests SBOM output during image build and
publishes GitHub build-provenance attestations when repository visibility
supports them. Treat those as separate supply-chain artifacts: validate
the image or release tarball signature first, then inspect SBOM/provenance
with your registry or GitHub attestation tooling when you need that extra
evidence. A successful `cosign verify` alone does not prove SBOM or
provenance contents.

The signing identity is the full GitHub Actions workflow reference:

- **Certificate identity pattern:**
  `^https://github.com/CodesWhat/sockguard/.github/workflows/release-from-tag.yml@refs/tags/.+$`
- **OIDC issuer:**
  `https://token.actions.githubusercontent.com`

If either value differs from what cosign finds in the signature, the
image was not produced by our release pipeline — **do not run it**.

## Prerequisites

Install cosign v3 or later. That's what the release pipeline signs with
(v3.1.3, pinned in `release-from-tag.yml`), and the `--bundle` commands below
assume the bundle format it emits:

```bash
# macOS
brew install cosign

# Linux (pre-built binary, pin the sha as you see fit)
curl -Lo cosign https://github.com/sigstore/cosign/releases/latest/download/cosign-linux-amd64
chmod +x cosign
sudo mv cosign /usr/local/bin/
```

## One-liner verify

Replace `<TAG>` with the release tag you're pulling (for example
`1.3.0` or `latest`):

```bash
cosign verify \
  --certificate-identity-regexp '^https://github.com/CodesWhat/sockguard/.github/workflows/release-from-tag.yml@refs/tags/.+$' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  ghcr.io/codeswhat/sockguard:<TAG>
```

A successful verification looks like:

```text
Verification for ghcr.io/codeswhat/sockguard:<TAG> --
The following checks were performed on each of these signatures:
  - The cosign claims were validated
  - Existence of the claims in the transparency log was verified offline
  - The code-signing certificate was verified using trusted certificate authority certificates
[{...}]
```

The last line is a JSON object with the signing certificate details;
any well-formed JSON there is proof the signature matched. If cosign
returns a non-zero exit code, the signature is missing or does not
match the expected identity.

## Pinning by digest

For reproducible deployments, prefer verifying and pulling by SHA256
digest rather than by tag — a tag can be re-pointed, a digest cannot.

```bash
# Resolve the current digest for a tag
digest=$(docker buildx imagetools inspect \
  ghcr.io/codeswhat/sockguard:<TAG> --format '{{json .Manifest.Digest}}' \
  | tr -d '"')

# Verify against the digest
cosign verify \
  --certificate-identity-regexp '^https://github.com/CodesWhat/sockguard/.github/workflows/release-from-tag.yml@refs/tags/.+$' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  "ghcr.io/codeswhat/sockguard@${digest}"

# Then reference the same digest in your compose file
# image: ghcr.io/codeswhat/sockguard@sha256:...
```

## If verification fails

**Do not run the image.** Treat a verification failure as a potential
supply-chain compromise until proven otherwise:

- Double-check you pasted the full `certificate-identity-regexp` and
  that the escaping survived your shell (`^`, `$`, and `.+` must all
  appear in the regex).
- Run `cosign version` and confirm you have cosign v3 or later. The `--bundle`
  commands here assume the Sigstore bundle format cosign v3 emits; the legacy
  `--signature` / `--certificate` form shown for older v1.7 tags doesn't.
- Try the verification again with a fresh registry pull; a stale
  cached manifest can sometimes produce confusing errors.
- If the identity or issuer values differ from the ones published
  here, stop — open a private security advisory via the process in
  [`SECURITY.md`](https://github.com/CodesWhat/sockguard/blob/main/SECURITY.md)
  so we can investigate.

## Verifying release tarballs

The GitHub release assets (`sockguard-v<TAG>.tar.gz`) are also
cosign-signed. From v1.7.5 onward the release workflow uploads a sigstore
bundle (`.sigstore.json`) alongside the tarball:

```bash
cosign verify-blob \
  --bundle "sockguard-v<TAG>.tar.gz.sigstore.json" \
  --certificate-identity-regexp '^https://github.com/CodesWhat/sockguard/.github/workflows/release-from-tag.yml@refs/tags/.+$' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  "sockguard-v<TAG>.tar.gz"
```

Same interpretation as the image verify: a clean exit code is a
passing signature, anything else means stop and investigate.

<Callout type="info">
  Sockguard v2 and later publish only the sigstore bundle above, and v1.7.5
  published it alongside the legacy assets. Older tags don't have it: v1.7.0,
  v1.7.1, v1.7.3 and v1.7.4 attach the earlier `.bundle` file plus a detached
  signature (`.sig`) and signing certificate (`.pem`), so the command above
  fails on those and you want the detached form instead. v1.7.2 has no GitHub
  release or release assets because its publish workflow failed.

  ```bash
  cosign verify-blob \
    --certificate "sockguard-v<TAG>.tar.gz.pem" \
    --signature   "sockguard-v<TAG>.tar.gz.sig" \
    --certificate-identity-regexp '^https://github.com/CodesWhat/sockguard/.github/workflows/release-from-tag.yml@refs/tags/.+$' \
    --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
    "sockguard-v<TAG>.tar.gz"
  ```

  Cosign's own `sign-blob` deprecated those output flags in favor of the
  bundle format. Use `--bundle` for current releases.
</Callout>

When release provenance is published, the release also includes
`sockguard-v<TAG>.tar.gz.intoto.jsonl`. Verify that attestation separately
from the tarball's cosign bundle before relying on it for SLSA evidence.

## Verifying the per-platform binary archives

`sockguard-v<TAG>.tar.gz` above is the **source** snapshot. The archives
you download to actually run sockguard are the per-platform ones,
`sockguard_<VERSION>_<OS>_<ARCH>.tar.gz` (note the underscores and the
missing `v`). They're easy to confuse, so check which file you have
before picking a command.

Each per-platform archive ships its own `.sigstore.json` bundle, and so
does `checksums.txt`. Verify a single archive directly:

```bash
cosign verify-blob \
  --bundle "sockguard_<VERSION>_linux_amd64.tar.gz.sigstore.json" \
  --certificate-identity-regexp '^https://github.com/CodesWhat/sockguard/.github/workflows/release-from-tag.yml@refs/tags/.+$' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  "sockguard_<VERSION>_linux_amd64.tar.gz"
```

Or verify `checksums.txt` once and check any archive against it, which is
the cheaper route when you're pulling several platforms:

```bash
cosign verify-blob \
  --bundle "checksums.txt.sigstore.json" \
  --certificate-identity-regexp '^https://github.com/CodesWhat/sockguard/.github/workflows/release-from-tag.yml@refs/tags/.+$' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  "checksums.txt"

sha256sum --check --ignore-missing checksums.txt
```

<Callout type="info">
  Sockguard v2 and later publish only `.sigstore.json` bundles. v1.7.5
  dual-published those bundles with the legacy `.sig`/`.pem` pair for the
  source tarball, checksums, and binary archives. v1.7.3-v1.7.4 published
  only the legacy pair for checksums and binary archives; v1.7.0-v1.7.1 did
  not sign those binary artifacts. v1.7.2 has no GitHub release or release
  assets because its publish workflow failed. Use the assets actually attached
  to the historical release rather than assuming every v1.7 tag has the same
  set.
</Callout>

From v1.7.3 onward the archives also carry GitHub build-provenance
attestations, which record the workflow and commit that produced them:

```bash
gh attestation verify "sockguard_<VERSION>_linux_amd64.tar.gz" \
  --repo CodesWhat/sockguard
```

From v1.7.1 onward each archive additionally ships a CycloneDX SBOM as
`sockguard_<VERSION>_<OS>_<ARCH>.tar.gz.cyclonedx.json`. v1.7.0's archives
carry neither an SBOM nor a signature.

## Reproducible Go binaries

Starting with the v2.4 development line, unsigned Go binaries have deterministic
build inputs. This applies to the binary bytes, not to tar/deb/rpm packages,
container images, SBOMs, provenance records or signing bundles. Existing releases
with wall-clock build dates aren't covered retroactively. Signature verification
and independent rebuilding answer different questions; use both when needed.

From a clone with the requested commit or tag available, run the checked-in
procedure. It defaults to committed `HEAD`, Linux/amd64 and the exact tag's version
(or `0.0.0-repro` for an untagged commit):

```bash
bash scripts/ci/go-reproducible.sh
```

For a particular release, pass its tag. For example, once v2.4.0 is published:

```bash
GOOS=linux GOARCH=amd64 bash scripts/ci/go-reproducible.sh v2.4.0
```

The script exports the same committed tree into two different directories, uses
the exact `toolchain` pinned by that tree's `go.mod`, and builds with two separate,
initially empty Go build caches. Go may download the pinned toolchain and modules;
module versions and checksums come from `go.mod` and `go.sum`. The shared module
download cache isn't an independent supply-chain verification. The linker package
is derived from that exported tree's module declaration, so the v3 procedure also
rebuilds v2.4 refs with their `/v2` version package.

The [GoReleaser configuration](https://github.com/CodesWhat/sockguard/blob/dev/v2.4/app/.goreleaser.yaml)
defines the v2.4 contract; the [v3 development configuration](https://github.com/CodesWhat/sockguard/blob/dev/v3.0/app/.goreleaser.yaml)
uses the corresponding `/v3` linker package. Both and the reproduction command use `CGO_ENABLED=0`, `-trimpath`, `-buildvcs=false`,
`-s -w`, and explicit version, full source commit and UTC commit-time metadata.
`BuildDate` now means the source commit date, not the release workflow's start time.
AMD64 uses `GOAMD64=v1`; ARM64 uses `GOARM64=v8.0`. The procedure clears ambient Go
flags, workspace and experiment settings. It prints the chosen inputs and SHA-256,
compares both binaries byte for byte, and removes its temporary sources/caches on
exit. Uncommitted working-tree edits aren't part of the build.

CI runs this comparison for Linux and Darwin, each on amd64 and arm64. A different
result fails that target. For a downloaded release, verify its signature, extract
the matching platform archive, hash its `sockguard` binary and compare that digest
with the script's printed digest. Compare the same source commit, version,
toolchain, target and build flags. The optional second argument overrides the
version, which is useful for reproducing a snapshot's displayed version.

The build contract follows Go's
[build flags](https://pkg.go.dev/cmd/go#hdr-Compile_packages_and_dependencies) and
GoReleaser's [reproducible-build guidance](https://goreleaser.com/customization/builds/builders/go/#reproducible-builds).
A successful two-build CI check is evidence of deterministic output for those
inputs. It isn't a claim that the compiler, dependencies or runner are trusted,
or that every published artifact has been independently reproduced.
